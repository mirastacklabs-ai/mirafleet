**Goal.** A complete admin GUI served by central, good enough that the user's full-product test

BRAND.md, safe by default (TLS, Host allowlist, CSRF, strict CSP, setup token), and audited with

Parallel agents share one worktree; steps in a wave touch disjoint files; no step touches `go.mod`
(M4 adds no module, §10).

## 1. Scope

**In M4**
- `internal/gui` (new): an HTTPS server inside `mirafleet central run`, `html/template` + htmx 2,
  every asset embedded with `go:embed`. No JS build step, no npm, no CDN, nothing loaded from the
  internet.
- Screens (§3): Setup, Login, Overview, Fleets, Runners, Join tokens, Operators, Workspaces,
  Audit, Account. They cover every `mirafleet central ...` admin command except `exec` (Q7) and
  `init`.
- One admin account, created on first start through a one-time setup token (Q4); password reset
  from the central CLI.
- Additive service, store and API changes the screens need: filtered audit reads, the fleet guard
  toggle (Q6), GUI admin and session storage (migration 0003), listing revoked runners.
- CLI parity for the new service functions: `central gui reset-admin`, `central fleet set NAME
  -confirm=BOOL`, filter flags on `central audit`.
- Tests: `TestM4Done` (httptest, real central), a route-table security suite, and a built-binary
  smoke test.

**Not in M4** (enterprise or later): more than one admin, RBAC, SSO/OIDC, 2FA/WebAuthn, ACME
certificates (central never calls out), running actions or workspace commands from the GUI (Q7),
fleet delete, audit retention, live streaming (SSE/websockets), i18n.

**Unchanged rules.** Lifecycle and admin operations stay on central only. The GUI is a second
front end on the same `*service.Service` methods as the admin socket, in the same process, with
source `gui`. Nothing in M4 adds a method to `api@mirafleet` or to MCP.

## 2. Design decisions

### 2.1 One code path
- The GUI calls `*service.Service` in-process (M2 §1.5). It never touches the store, the registry
  or the SSH server directly, so a revoke from the GUI is the same tombstone → kick → commit path
  as `central runner revoke` (`service.lifecycle`).
- The GUI depends on a narrow interface, `gui.Backend`, listing exactly the service methods it
  uses; `*service.Service` satisfies it (compile-time assertion in `internal/gui/backend.go`). This
  is also the enterprise seam (RBAC/SSO wrap it).
- Principal: `auth.GUIAdmin(username, remote)` (new, next to `auth.LocalAdmin`) returns
  `Principal{Kind: KindAdmin, Name: <username>, Remote: <TCP peer ip:port>}`. Source is always
  `service.SourceGUI`. The policy is unchanged (`TablePolicy`: admin may do everything); admin-only
  service methods keep their double gate.
- Import rule (new `TestGUIDeps` in `cmd/mirafleet/deps_test.go`): `internal/gui` never imports
  `internal/store/sqlite`, `internal/central`, `internal/central/registry`, `internal/apiclient`,
  `internal/orch`, `internal/mcpserver`, `modernc.org/*` or `github.com/containerd/*`. It is wired
  only from `cmd/mirafleet/central_linux.go`, so darwin/windows binaries never link it (extend
  `TestNoSQLiteOnNonLinux`'s target loop with a positive control: linux links `internal/gui`).

### 2.2 Listener, TLS and bind address
- Flag `central run -gui-listen ADDR`, **default `0.0.0.0:8443`** (Q11, user decision); `off`
  disables the GUI. Any address is allowed with either certificate.
- **TLS always** (Q2). No plain-HTTP mode: `Secure` + `__Host-` cookies, and no downgrade path to
  get wrong. TLS 1.3 minimum, stdlib `crypto/tls` only.
- **Certificate.** If `-gui-cert FILE -gui-key FILE` are given (both or neither), use them
  (PEM; key file must be 0600/0400 and owned by central's uid, checked like `keys` does).
  Otherwise central generates a self-signed ECDSA P-256 certificate on first GUI start
  (`<data>/gui/tls.crt`, `<data>/gui/tls.key` 0600, dir 0700, written through `os.Root` on the data
  dir), validity 2 years, regenerated when it has under 30 days left or when the `-gui-host` set
  changes. SANs: `localhost`, `127.0.0.1`, `::1`, the short and full `os.Hostname()`, every
  `-gui-host` name and the non-link-local interface IPs present at generation time (a later IP
  change does not regenerate it: the Host allowlist below, not the SAN list, decides access).
- **Startup notice.** Every start logs the GUI URL(s), the certificate's SHA-256 fingerprint and,
  for a wildcard or non-loopback bind, a notice:
  `GUI is reachable on all interfaces (0.0.0.0:8443). To restrict it: -gui-listen 127.0.0.1:8443
  (then use ssh -L), -gui-listen off, or a firewall rule for port 8443.` With the self-signed
  certificate it adds: `Check that your browser's certificate fingerprint matches <fp> before you
  type the setup token or your password.` The same text is on the Account screen.
- **HSTS** only with an operator certificate (any bind). Never with the self-signed one: HSTS
  ignores the port, so it would also hit other services on that host name, and it removes the
  browser's "proceed anyway" button, locking the admin out.
- **Host header allowlist** (DNS-rebinding defence), checked before routing; anything else, and a
  missing `Host`, gets 421. DNS rebinding always makes the browser send the **attacker's** host
  name (for example `rebind.evil.example`), never an IP literal of the victim, so the rule is: IP
  literals only if they are this machine's own addresses, names only if listed exactly.
  - Accepted IP literals: `127.0.0.1`, `::1` and every address of every up interface
    (`net.Interfaces` + `Addrs`, IPv4 and global/ULA IPv6; link-local excluded), read at start
    and refreshed every 60 s, so a DHCP change is picked up. `0.0.0.0`/`::` are never accepted.
  - Accepted names: `localhost`, the short and full `os.Hostname()`, the DNS SANs of an operator
    certificate, and the comma-separated `-gui-host NAME,...` list (for the names admins type,
    e.g. `central.example.com`). Exact match only, case-insensitive, one trailing dot trimmed; no
    wildcards, no suffix matching, no reverse DNS (central never resolves names for this).
  - Any port is accepted (`ssh -L` and proxies remap ports). IPv6 literals must be bracketed.
  - Wildcard-DNS names that embed an IP (`192-168-1-5.nip.io` style) are refused unless listed:
    they are attacker-controllable names.
  - Second layer: with the self-signed certificate a rebinding name also fails the TLS name check,
    and the `__Host-` cookie is never sent to another host name.
- **Reverse proxies:** supported only as TLS to TLS (the proxy talks HTTPS to central and must send
  an allowed `Host`). `X-Forwarded-*` is never trusted: the remote in audit rows and the rate-limit
  key is the TCP peer. Documented in the guide.
- `-advertise HOST:PORT` (new, optional) is the SSH address shown in copy-paste command hints
  (`runner join`, `mcp login`). Default: `-listen` if it names a host, else `<central-host>:<port>`
  with a note to replace it.

### 2.3 Admin bootstrap and recovery (Q4)
- Migration `0003_gui.sql` adds `gui_admins` and `gui_setup` (§2.9). One active admin at most.
- **First start.** When the GUI starts and no active admin exists, `service.EnsureGUISetup`
  creates a setup token (32 random bytes, `mfs1.<base64url>`), stores only its SHA-256 with a 24 h
  expiry in `gui_setup` (audited `gui.setup_token`, the token never), and the GUI writes the token
  to `<data>/gui/setup-token` (0600, `O_EXCL` through `os.Root`). The log says where the file is and
  the URL to open; it never prints the token (journald is often readable by group `adm`).
- `/setup` exists only while no active admin exists. The form takes the token, a username
  (`store.OperatorNameRE` shape) and the password twice. `service.CompleteGUISetup` checks the
  token in the same transaction that inserts the admin and deletes the setup row (two concurrent
  setups: one wins, the other gets `conflict`). The GUI then deletes the token file and logs the
  admin in (new session). Audited `gui.setup`.
- **Recovery.** `mirafleet central gui reset-admin` (admin socket, new admin method
  `gui.reset_admin`) sets the active admin to `reset`, deletes every GUI session row in the same
  transaction, creates a fresh setup token and prints it once on the CLI's stdout (the caller
  already has central's uid, as trusted as the file). Audited `gui.reset_admin`, source `cli`.
- Expired setup token: the GUI makes a new one at the next start; `reset-admin` also works with no
  admin at all.
- **Setup reachable from the LAN** (Q11 default `0.0.0.0`). Checked case by case:
  - *Guessing the token:* 256 bits, constant-time compare, per-IP bucket on `/setup`, 24 h expiry.
    Not feasible.
  - *Racing the admin:* the token is the only credential; without it nothing can be created. No
    endpoint regenerates or invalidates the token, so a LAN attacker cannot deny setup either.
  - *Information before setup:* every route except `/setup`, `/static/` and error pages redirects
    to `/setup`; no data, version or fingerprint is shown, and no service method other than
    `CompleteGUISetup` is reachable.
  - *Man in the middle on the first visit* (self-signed certificate, admin clicks through): the
    only real risk. The startup notice tells the admin to compare the fingerprint first, the
    setup page says it again next to the token field, and the guide recommends doing setup over
    `ssh -L 8443:127.0.0.1:8443`. After setup, a leaked token is useless (single use, row deleted).
  - *After setup* `/setup` is 404, so the LAN sees only `/login` (rate-limited, §2.5).

### 2.4 Passwords and sessions
- **Hashing** (Q1): Argon2id from `golang.org/x/crypto/argon2` (module already in go.mod; §10).
  Parameters `t=3, m=64 MiB, p=2`, 16-byte salt, 32-byte key, stored as a PHC string
  (`$argon2id$v=19$m=65536,t=3,p=2$<salt>$<hash>`). `auth.HashPassword`, `auth.VerifyPassword`
  (constant-time), `auth.NeedsRehash` (new file `internal/auth/password.go`). Login re-hashes
  when the parameters changed. Unknown usernames are verified against a fixed dummy hash, so
  timing does not reveal the username. bcrypt was rejected: it silently ignores bytes past 72.
- **Password rules:** 12 to 256 bytes of valid UTF-8, not equal to the username, not all one
  character. No composition rules (NIST SP 800-63B). Change needs the current password.
- **Hashing cost bound:** at most 2 hashes run at once (semaphore in the GUI); the rest wait up to
  5 s, then get 503. Rate limits (§2.5) apply before hashing.
- **Sessions in SQLite (Q5, user decision)**, table `gui_sessions` in migration 0003 (§2.9), so
  they survive a central restart. Token = 32 random bytes, base64url, in cookie
  `__Host-mf_session` (`Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, no `Domain`, no
  `Max-Age`). The row stores only `SHA-256(token)` (the token has 256 bits of entropy, so a fast
  hash is enough); lookups are by that hash. Row: admin id, the admin's credential generation at
  login, created, last active, absolute expiry, remote, a user-agent summary (clipped to 128 B).
- **A DB copy cannot hijack a session:** nothing stored is a cookie value or derives one. The
  CSRF key is not stored either: it is `HMAC-SHA256(token, "mirafleet-gui-csrf-v1")`, computed
  from the cookie on each request (§2.6). Tested in S14.
- Idle timeout 30 min (from last active), absolute 12 h (from login), at most 16 sessions per
  admin (the oldest row deleted in the same transaction as a new one). Login always creates a new
  token (no fixation), atomically with its `gui.login` audit row; logout deletes the row with its
  `gui.logout` row and expires the cookie.
- **Bound to the credential generation.** Every request runs one indexed read joining the session
  row to the active admin (`service.GUIAuthenticate`). A session whose admin is not active, or
  whose generation differs, or that is past either expiry, is dead and its row deleted. A password
  change bumps the generation, deletes every other session row and re-issues the current session
  with a new token, all in one transaction; `reset-admin` deletes all rows (§2.3). Both take effect
  on the very next request.
- **Last-active writes** are throttled: at most one `TouchGUISession` per session per 60 s
  (idle precision ±60 s). Touches are not audited (like `TouchRunner`).
- **Passive requests:** fragment endpoints polled by htmx (`hx-trigger="every 10s"`) are marked
  passive at route registration and never touch the row, so an open tab does not keep a session
  alive forever.
- **Clean-up:** expired and dead rows are deleted at GUI start and every 10 min
  (`PurgeGUISessions(now)`, not audited: housekeeping, not a change anyone asked for).
- Expired or missing session: normal requests get 303 to `/login?next=<path>` (`next` must be a
  local path, checked); htmx requests get 200 with `HX-Redirect: /login`.

### 2.5 Login rate limits and lockout
- Per client IP (IPv6 by /64): token bucket of 5 attempts per minute; after 10 consecutive
  failures that IP is locked out for 15 min (429 with a `Retry-After`). A success resets its count.
- Global: more than 100 failures in 10 min switches login to one attempt per 5 s for everyone, and
  logs a warning. It never hard-locks the account: with one admin, an account lockout would be a
  free denial of service.
- `/setup` has the same per-IP bucket.
- Failed logins are logged (IP, username clipped to 64 bytes, never the password), not audited,
  following M2 §1.7. A lockout writes one `gui.lockout` audit row per IP per lockout window
  (bounded). Successful login and logout are audited (`gui.login`, `gui.logout`).
- Limiter maps are hard-capped (4096 entries, LRU), like `ipLimiter` in `internal/central`.

### 2.6 CSRF and request hygiene
Three independent layers on every unsafe method (POST; the GUI uses no PUT/PATCH/DELETE):
1. `http.CrossOriginProtection` (stdlib since Go 1.25): refuses cross-origin requests by
   `Sec-Fetch-Site` and `Origin`.
2. Synchronizer token: `HMAC-SHA256(csrfKey, "form")` with the per-session key derived from the
   cookie token (§2.4, never stored), sent as a
   hidden `_csrf` field in every form and as `X-CSRF-Token` for htmx (`hx-headers` on `<body>`, plain
   JSON). Compared in constant time. `/login` and `/setup` use a pre-session token in a short-lived
   `__Host-mf_pre` cookie (double submit, also `SameSite=Strict`).
3. `SameSite=Strict` session cookie.

Also: forms only `application/x-www-form-urlencoded` (anything else 415); bodies capped at 64 KiB
with `http.MaxBytesReader` (413); `ParseForm` only after the cap; unknown form fields ignored, never
mapped by reflection. Every POST is followed by a redirect (303, PRG) except the two that show a
secret once (token create, registration code), which render directly with `no-store`.

### 2.7 Security headers and CSP
Set by middleware on every response, errors and static files included:

| Header | Value |
|---|---|
| `Content-Security-Policy` | `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `no-referrer` |
| `X-Frame-Options` | `DENY` |
| `Cross-Origin-Opener-Policy` | `same-origin` |
| `Cross-Origin-Resource-Policy` | `same-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), usb=(), payment=(), clipboard-read=()` |
| `Cache-Control` | `no-store` on HTML, fragments and exports; `public, max-age=31536000, immutable` on content-hashed static URLs |
| `Strict-Transport-Security` | §2.2 rule only |

**No `unsafe-inline`, no `unsafe-eval`.** This is feasible with htmx 2 under these rules:
- htmx config in `<meta name="htmx-config">` (JSON, read with `JSON.parse`):
  `{"allowEval":false,"allowScriptTags":false,"includeIndicatorStyles":false,"historyCacheSize":0,"refreshOnHistoryMiss":true,"selfRequestsOnly":true,"defaultSwapStyle":"outerHTML","responseHandling":[{"code":"204","swap":false},{"code":"[23]..","swap":true},{"code":"422","swap":true},{"code":"[45]..","swap":false,"error":true}]}`.
  `historyCacheSize: 0` keeps page snapshots (which may hold a join token) out of `localStorage`.
- Templates never use `hx-on*`, trigger filters (`[...]`), `js:`/`javascript:` values, `hx-vars`,
  `style="..."`, `on*=` attributes or inline `<script>`. Allowed htmx attributes: `hx-get`,
  `hx-post`, `hx-target`, `hx-swap`, `hx-trigger` (`load`, `every Ns`, `change`, `submit`,
  `keyup changed delay:Ns`), `hx-select`, `hx-confirm`, `hx-indicator`, `hx-headers` (on body), `hx-disabled-elt`,
  `hx-include`. A template lint test (S14) enforces both lists.
- The only scripts: `/static/<hash>/htmx.min.js` (vendored) and `/static/<hash>/app.js` (ours,
  under 150 lines, no dependencies): copy-to-clipboard buttons, the registration-code countdown,
  and `<time>` relative-age refresh. Everything works without JavaScript (§3.12).

### 2.8 Server limits and robustness
- `http.Server`: `ReadHeaderTimeout 5s`, `ReadTimeout 15s`, `WriteTimeout 60s`, `IdleTimeout 120s`,
  `MaxHeaderBytes 16 KiB`, `ErrorLog` routed to central's `logf`.
- Per-route context timeout: 15 s default; `KillWorkspace` the admin socket's `wsCloseOuterTimeout`;
  audit export 5 min (it extends its own write deadline with `http.ResponseController`).
- At most 32 requests in flight (503 beyond); panics recovered into a branded 500 page with a
  request id, logged with the stack, no detail to the browser.
- Access log line per request: method, route pattern (not the raw path with ids), status, duration,
  remote, request id. Never cookies, form values, tokens or the query string of `/setup`/`/login`.
- Errors shown to the admin come from `service.ToAPIError` messages (fixed per code, no SQL, no
  paths), plus our own field-level validation text.
- Shutdown: `http.Server.Shutdown` with 5 s, before the SSH server and the store close (in
  `startCentral`'s close function).

### 2.9 Store and service additions

**Migration `internal/store/sqlite/migrations/0003_gui.sql`** (forward-only, contiguous numbering
test already exists):
```sql
CREATE TABLE gui_admins (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    username    TEXT    NOT NULL,
    pw_hash     TEXT    NOT NULL,
    generation  INTEGER NOT NULL DEFAULT 1 CHECK (generation >= 1),
    status      TEXT    NOT NULL CHECK (status IN ('active', 'reset')),

CREATE UNIQUE INDEX gui_admins_one_active ON gui_admins (status) WHERE status = 'active';

    created_at  INTEGER NOT NULL
);
CREATE TABLE gui_sessions (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    token_hash     BLOB    NOT NULL UNIQUE CHECK (length(token_hash) = 32),
    admin_id       INTEGER NOT NULL REFERENCES gui_admins (id) ON DELETE CASCADE,
    generation     INTEGER NOT NULL CHECK (generation >= 1),
    created_at     INTEGER NOT NULL,
    last_active_at INTEGER NOT NULL,
    expires_at     INTEGER NOT NULL,   -- absolute expiry (created + 12 h)

CREATE INDEX gui_sessions_admin   ON gui_sessions (admin_id);
CREATE INDEX gui_sessions_expires ON gui_sessions (expires_at);
CREATE INDEX audit_actor   ON audit (actor);
CREATE INDEX audit_request ON audit (request_id) WHERE request_id <> '';
```

- The admin socket's `handleAuditList` moves onto `service.ListAudit` (removes the handler-local
  gate and its comment "The service has no audit read"); `api.AuditListParams` gains optional,
  additive filter fields (`fleet runner actor source outcome action action_prefix workspace
  request_id from to before_id`).
- New admin methods in `internal/api/api.go` (`MethodGUIResetAdmin = "gui.reset_admin"`,
  `MethodFleetSetConfirm = "fleet.set_confirm"`), added to `IsAdminMethod`, to `adminTable()` in
  `internal/central/admin.go` and to any test that enumerates admin methods (they must stay refused
  on `api@`). No policy change.
- Secrets never leave the service except where the caller needs them once: the setup token
  (to the GUI at start, to the CLI on reset), a join token (create), the registration code (show).
  Password hashes and session token hashes never leave the store/service boundary; `GUIAdmin` and
  session views in the GUI carry username, ids, remote, user agent and timestamps only. The raw
  session token exists only in the cookie and in the response that sets it.
- The service owns the session clock (`service.Config.Now`), so expiry is testable with an
  injected clock and is the same after a restart.

### 2.10 Rendering
- Go 1.22 `http.ServeMux` patterns with methods (`GET /runners/{fleet}/{runner}`), stdlib only.
- Templates: `internal/gui/templates/*.html`, parsed once at start from `embed.FS`; one layout, one
  file per screen, partials named `<screen>/<part>`. A request is either a full page or, with
  `HX-Request: true`, the fragment named by the route. Same handler, same data.
- View models only: handlers map service results into small view structs. Never pass a store row
  that carries secret material (`JoinToken.SecretHash`, `Runner.PubKey`, `GUIAdmin.PwHash`) to a
  template. `template.HTML`/`template.JS`/`template.URL` are banned outside one vetted helper file
  (lint test).
- Untrusted text (runner names, labels, heartbeat `Info`, advertised actions and patterns,
  hostnames, session ids, image refs, audit params) is rendered as text only; long values are
  clipped with a full-value `title`. Path segments built with `url.PathEscape`.
- Times: UTC ISO 8601 in `<time datetime>` plus a relative age; durations human-readable.
- Flash messages (one-shot, after a PRG redirect) travel in a short-lived `__Host-mf_flash` cookie
  holding a message id from a fixed table plus its subject, MACed with the session's CSRF key; an
  invalid one is ignored. No DB write per flash. Shown in an `aria-live="polite"` region.
- Static assets: `/static/<sha256-prefix>/<name>`; the hash is computed at start from the
  embedded bytes, so caches never serve stale files.

## 3. Screens

Every screen: page title, breadcrumb, primary action top right, table with sticky header and an
empty state that says what to do next (with the CLI equivalent), loading indicator on htmx
requests, field-level errors (422 swaps the form), destructive actions in red (`--bad`) behind a
confirmation. Status badges use BRAND's status colours with the status word (never colour alone).

### 3.1 Setup and Login
- `/setup` (only without an admin): token, username, password ×2, strength hint (length only),
  and the line "Before you type the token, check that the certificate fingerprint in your browser
  is `<fp>`, as printed in central's log" (§2.3).
- `/login`: username, password; generic error "Wrong username or password"; lockout message with
  minutes left. `next` honoured if local.
- After setup or login: Overview.

### 3.2 Overview (`/`)
- Cards: fleets (by mode), runners by status (pending highlighted with a link "N waiting for
  approval"), online vs offline, live workspaces, join tokens usable now.
- Pending runners list with Approve buttons inline.
- Recent audit (last 15 rows) and recent `denied` rows (last 24 h, up to 15).
- Polls every 10 s (passive).

### 3.3 Fleets (`/fleets`, `/fleets/{fleet}`)
- List: name, mode, guarded, runners (non-revoked), workspace summary (executor, default image,
  network).
- Create (`/fleets/new`): name, mode (radio), guarded. Workspace mode shows the workspace config
  fields that `central fleet create` takes (executor, default image, images allowlist, pull,
  network, egress, cpus, memory, pids, tmpfs, disk, idle TTL, max TTL, exec default, exec max),
  with the defaults from `service.WorkspaceDefaults` pre-filled and units parsed the same way as the
  CLI (shared parser moved from `cmd/mirafleet/admin_workspace.go` into a pure package,
  `internal/workspace/units`, if it is not already importable).
- Detail: summary, runners of the fleet (Runners table filtered), tokens of the fleet, workspace
  config (full, admin view) with Edit → `SetFleetWorkspace`, guard toggle (Q6): turning the guard
  **off** asks to type the fleet name.

### 3.4 Runners (`/runners`, `/runners/{fleet}/{runner}`)
- List across fleets: fleet, name, status badge, online dot + last heartbeat age, trusted labels
  (from the token), executor and free/total slots (workspace runners), version. Filters: fleet,
  status, online, "show revoked" (`ListRunnersAll`). Polls every 10 s (passive).
- Actions per status: pending → Approve, Revoke; active → Disable, Revoke; disabled → Enable,
  Revoke. Revoke opens a confirmation that explains the effect (connection closed, in-flight work
  cancelled, workspaces closed, key never re-enrols) and asks to type `fleet/runner`.
- Detail: identity (fingerprint, joined, token id), heartbeat info (hostname, OS, arch, version,
  load), trusted vs informational labels side by side, **advertised actions** with parameter
  names, patterns and defaults (M5 action discovery; marked "informational: the runner's
  actions.yaml decides"), live workspaces on this runner, last 20 audit rows for it.

### 3.5 Join tokens (`/tokens`)
- List: id, fleet, labels, auto-approve, uses/max, expires (relative), state (usable, used up,
  expired, revoked). Filter by fleet; "show finished" toggle.
- Create: fleet, labels (key=value rows), auto-approve, uses (1–1000), TTL (≤ 30 d). The result
  panel shows the token **once** with a copy button, the expiry, and the command to run on the
  runner (`mirafleet runner join <advertise> -name NAME -token -`, then paste the token on stdin).
  The panel says the token cannot be shown again. A one-time form nonce (MACed with the session's
  CSRF key; used nonces kept in memory, 1 h, LRU 1024) makes a resubmitted form (back button,
  refresh) say "already created; the token is not shown again" instead of minting a second token.
- Revoke (simple confirm).

### 3.6 Operators (`/operators`)
- List: name, fingerprint, status, registered, last seen. Revoke with type-the-name confirmation
  (effect: connections dropped, execs cancelled, workspaces reaped).
- Registration code panel: hidden until "Show code" (each show is audited by
  `service.OperatorCode`, so it never auto-refreshes). Shows the code, the seconds left (countdown in
  `app.js`, static number without JS), central's host-key fingerprint, and the command
  `mirafleet mcp login <advertise> -name NAME -code -`. When it expires: "Show the next code".
- Rotate secret: confirmation explaining that every code shown so far stops working.

### 3.7 Workspaces (`/workspaces`)
- List (`AdminListWorkspaces`): id (short, full in title), fleet, runner, operator, session, image,
  state badge, created, last used, expires, age. Filters: fleet, state (live / all). Polls every
  10 s (passive).
- Kill with confirm; shows the resulting state (`closed`, or `closing` when the runner is offline,
  with the explanation that the reaper finishes it).

### 3.8 Audit (`/audit`)
- Filters: time range (from/to, UTC), fleet, runner, actor, source (`cli api gui enroll system`),
  outcome, action (exact or prefix, e.g. `runner.`), workspace, request id. Filters live in the
  query string, so a filtered view can be bookmarked.
- Table newest first, keyset paging (Older/Newer by id), 50 rows per page; a row expands to show
  params, message, exit code, duration and request id; "same request" link filters by request id.
- Export: CSV or JSON Lines of the current filter, oldest first, streamed, at most 100,000 rows
  (the response says when it was cut). `Content-Disposition: attachment`. CSV cells starting with
  `=`, `+`, `-`, `@`, tab or CR get a leading `'` (formula injection). Each export first writes an
  `audit.export` row with the filter.

### 3.9 Account (`/account`)
- Change password (current, new ×2). Signs out every other session.
- Active sessions: created, last active, remote, browser summary, "this session"; sign out one or
  all others.
- About: mirafleet version, central host-key fingerprint, GUI certificate fingerprint and expiry,
  GUI listen address, SSH advertise address.

### 3.10 Errors
Branded 403, 404, 413, 415, 421, 429, 500 and 503 pages (full page or fragment), each with a
request id. 404 for unknown resources never reveals whether something exists in another form.

### 3.11 Look and feel (BRAND.md)
- Tokens exactly as BRAND.md, light and dark via `prefers-color-scheme`, with a theme switch
  (light / dark / system) stored in a non-secret `mf_theme` cookie set by a POST, so the server
  renders `data-theme` and there is no flash.
- Header: three-bar mark (inline SVG in the layout), `MIRAFLEET` wordmark, `BY MIRASTACK LABS` on
  wide screens; nav with the active item underlined in `--signal`. Oswald for display and body,
  JetBrains Mono for labels, ids, table data and code. 2px radius controls, 4px panels, hairline
  borders, no shadows. Signal orange only for emphasis and the focus ring.
- Responsive to 360 px: nav collapses into a `<details>` menu (no JS), tables scroll inside their
  panel.

### 3.12 Accessibility and no-JS
- Semantic HTML, every input labelled, visible focus ring, skip link, `aria-current` on nav,
  confirmations as real pages/forms (keyboard reachable), status text not colour-only, WCAG AA
  contrast for all token pairs used for text (checked by a test, S16).
- Every action works with JavaScript off: forms POST and redirect; htmx only enhances (partial
  swaps, polling).

## 6. "M4 done when"

### 6.1 `TestM4Done` (`internal/central/m4_done_test.go`)
In-process real central (SQLite in `t.TempDir()`, registry, service, SSH on `127.0.0.1:0`) from
`newEnv`, `m3Enrol` and the fake executor, keys generated at test time. The GUI is
`gui.New(gui.Config{Backend: e.svc, DataDir: t.TempDir(), Now: clock.Now, ...})` mounted with
`httptest.NewUnstartedServer(srv.Handler())`, `ts.TLS = srv.TLSConfig()`, `ts.StartTLS()`; the
client trusts only the GUI's self-signed certificate, uses `net/http/cookiejar`, and sends
`Origin`/`Sec-Fetch-Site` like a browser. One offset clock (real time plus an advance the test
controls) is injected into both the service (`newEnvOpts` gains a service-clock option) and the
GUI, since session expiry is enforced in the service.

1. **Bootstrap.** Every page redirects to `/setup`; `<data>/gui/setup-token` is 0600; `/login`
   refuses; a wrong token is refused; the right token creates `admin`, removes the file, logs in;
   `/setup` is now 404; a second token use fails.
2. **Cookies and headers.** Session cookie is `__Host-mf_session`, `Secure`, `HttpOnly`,
   `SameSite=Strict`, `Path=/`; the token changes at login; CSP is exactly §2.7's; `Host:
   evil.example` → 421.
3. **CSRF.** A POST without `_csrf` → 403; with `Sec-Fetch-Site: cross-site` → 403; with a token
   from another session → 403; nothing changed, no audit row.
4. **Login limits.** 10 wrong passwords from one IP → 429; advancing the clock 15 min unlocks;
   unknown user and wrong password give the same page.
5. **Fleets.** Create `prod` (actions, guarded) and `dev` (workspace, image allowlist); an invalid
   name → 422, nothing created; the guard toggle on `prod` without the typed name is refused.
6. **Join token → runner.** Create a token for `prod`: shown once, `no-store`; the list never has
   the secret; replaying the form shows no token. A runner `db-1` joins with it over the real enroll
   SSH path → appears `pending` on `/runners`; Approve → `active`; it heartbeats → online, and its
   detail page lists `tail-logs` with its pattern.
7. **Revoke cascade.** An operator (registered in step 8's way) starts a long `action.run` on
   `db-1` over `api@`; Revoke from the GUI with the wrong typed name is refused; with `prod/db-1`
   the action ends `cancelled`, message `runner revoked`, and a reconnect is refused at auth: the
   same path as `TestM2Done`.
8. **Operators.** "Show code" returns a code (audit row `operator.code`, `source=gui`, code not in
   it); `alice` registers with it over SSH; she is listed; Rotate secret → the old code is refused;
   Revoke `alice` → her connection drops.
9. **Workspaces.** `bob` opens a workspace on `dev` (fake executor); the GUI lists it with runner
   and session; Kill → `closed`, fake executor got the destroy.
10. **Audit.** Filter `source=gui` shows only GUI rows and every GUI change above is there with
    `actor=admin` and the client's remote; filter by fleet and by action prefix `runner.`; paging
    both ways; CSV export has a header, neutralises a crafted `=cmd` value, and is preceded by an
    `audit.export` row; JSONL parses line by line.
11. **Sessions.** A polled fragment does not extend the idle timer: advancing the clock 31 min
    while polling → next normal request redirects to `/login`, an htmx one gets `HX-Redirect`.
    Advancing past 12 h kills an active session too. Logout makes the old cookie useless (row
    gone).
12. **Restart and credential binding.** Log in sessions A and B. Discard the `gui.Server` and the
    `service.Service`, then build new ones over the same SQLite file (closing and reopening the
    DB): A and B still work with their cookies, so no session state lived in memory. A password
    change from A → A keeps working with its re-issued cookie, B is refused on its very next
    request and its row is gone. `service.ResetGUIAdmin` (admin socket principal, source `cli`)
    → A is refused at once, `gui_sessions` is empty, a new setup token is returned.
    `PurgeGUISessions` after the clock passes both expiries leaves no expired rows.
13. **Hygiene.** No response after the creation response contains the join token; no response ever
    contains the registration secret, a password hash, the setup token (it exists only in the file)
    or private key material; `gui_sessions` holds no cookie value (only 32-byte hashes); every state
    change made through the GUI has its audit row with `source=gui`; no GUI action wrote a row with
    `source=api`.

- **S1:** parameterised SQL, `LIKE` escaping, one active admin enforced by the index and by the tx,
  constant-time token compare, generation CAS, every mutator atomic with its audit row, setup row
  deleted on success; `gui_sessions` stores only token hashes; password change and reset delete
  sessions in the same tx; purge cannot delete a live session; one admin cannot delete another's.
- **S2:** Argon2id parameters bounded on parse (no attacker-chosen 4 GiB `m` from a stored hash),
  constant-time verify, dummy hash for unknown users, UTF-8 and length rules.
- **S3:** no `style=`/inline script; tokens exactly BRAND.md; focus ring visible in both themes.
- **S4:** double gate on every admin method; new methods refused on `api@` for every principal;
  secrets returned only where §2.9 says; one login error; no audit row contains a token, code or hash;
  session expiry and generation checks on every request, on the service clock; passive never touches.
- **S5:** startup notice on every wildcard/non-loopback bind; TLS 1.3 min; HSTS never with the
  self-signed cert; Host allowlist exact (no suffix, no wildcard, no reverse DNS, no `0.0.0.0`,
  only own interface IPs) and checked before routing; interface refresh cannot widen to foreign
  addresses; headers on every path including errors and static; limits before parsing; no detail in
  500s; key file permissions.
- **S6:** token entropy, cookie attributes, CSRF key derived from the cookie and never stored,
  flash/nonce MACs, passive marking, limiter maps bounded, /64 bucketing, CSRF layers independent,
  constant-time.
- **S7–S11:** every POST behind `requireAdmin` + CSRF; PRG; secret-once pages `no-store` and never
  stored in session/flash; untrusted runner data inert (XSS tests); URL building escaped; no store
  row with secret fields reaches a template; revoke/rotate/guard-off need typed confirmation;
  export formula-safe and audited first.
- **S12:** flags validated; GUI stops before the store closes; startup log has no token; CLI
  `reset-admin` prints the token only to stdout; `internal/gui` not linked on darwin/windows.
- **S13–S16:** tests use ephemeral ports, `t.TempDir()`, generated keys, injected clock; no sleeps
  as synchronisation; route-table suite covers routes added later automatically.
- **All:** no new module; lifecycle/admin still unreachable from `api@` and MCP; every GUI change
  audited with source `gui`; works with JavaScript off.

## 8. Risks

| Risk | Mitigation |
|---|---|
| htmx features that need `eval` silently fail under the strict CSP | config meta with `allowEval:false`; attribute allowlist enforced by the template lint (S14); S19 browser check with the console open |
| GUI reachable from the whole LAN by default (`0.0.0.0:8443`, user decision) | startup notice with the three ways to restrict it; setup needs the 256-bit token from a 0600 file; login rate limits and Argon2id; Host allowlist; guide recommends a firewall rule for 8443 |
| Man in the middle on the first (self-signed) visit captures the setup token or password | fingerprint in the log, on `/setup` and Account; guide says to compare it or do setup over `ssh -L`; operator certificate option; a used setup token is worthless |
| Self-signed certificate warnings confuse admins | same fingerprint checks; how to use `-gui-cert`; no HSTS so "proceed" stays possible |
| Session table copied (backup, stolen disk) | only SHA-256 of 256-bit tokens stored, CSRF key derived from the cookie; S14 tries every stored value as a cookie |
| Session rows grow or go stale | 16 per admin, purge at start and every 10 min, dead rows deleted on use |
| Touch writes on every request | throttled to one per session per 60 s; passive requests never write |
| Argon2 memory used as a DoS lever (64 MiB per attempt) | rate limits before hashing, 2 concurrent hashes, 5 s queue then 503 |
| Single admin locked out by an attacker | per-IP lockout only, global slow-down instead of lock, CLI `reset-admin` |
| DNS rebinding against a GUI bound to all interfaces | Host allowlist (own interface IPs, hostname, `localhost`, `-gui-host` only; exact match), TLS name check, `__Host-` cookie scoping |
| Host allowlist too strict for a name admins use (DNS alias, proxy) | clear 421 page naming `-gui-host`; the guide lists the accepted forms |
| Clickjacking | `frame-ancestors 'none'`, `X-Frame-Options` |
| CSRF on revoke/rotate | three independent layers, typed confirmations on the worst actions |
| XSS from runner-controlled data (heartbeat info, labels, action patterns) | html/template only, banned `template.HTML`, hostile-data tests, CSP as backstop |
| Secrets cached or persisted by the browser (join token, code) | `no-store`, htmx `historyCacheSize:0`, never in session/flash/URL |
| Polling keeps sessions alive or floods the audit table | passive routes; polled endpoints are reads (no audit); the code panel never polls |
| Long service calls (kill on a slow runner, export) hit server timeouts | per-route timeouts, `ResponseController` deadlines for export |
| Store interface grows (enterprise Postgres later) | narrow, typed methods with `storetest` coverage; no generic SQL |
| Binary size (fonts ~0.4 MB, htmx ~50 KB) | accepted; fonts are the only large assets |
| Port 8443 also the runner `tls-front` default (`127.0.0.1:8443`), which collides with a `0.0.0.0:8443` GUI on the same host | different hosts in practice; central fails at start with "address in use" naming `-gui-listen`; guide notes it |
| Visual quality cannot be judged from tests alone | style guide page, contrast test, screenshots (Q12), user check in S19 |

## 11. Decisions (14 Nov 2026) and ETA

All twelve questions are decided. Ten follow the recommendation; Q5 and Q11 were changed by the
user (the draft's recommendation is kept in brackets for the record).

1. **Password hashing: Argon2id** (`x/crypto/argon2`, already-approved module), `t=3, m=64 MiB,
   p=2`, PHC string, rehash on login when parameters change (§2.4). bcrypt rejected (72-byte limit).
2. **TLS always on**, no plain-HTTP mode; self-signed ECDSA P-256 by default, operator certificate
   optional (§2.2).
3. **HSTS only with an operator certificate**, on any bind. The draft's "non-loopback needs an
   operator certificate" rule is superseded by Q11.
4. **Bootstrap: setup token** in `<data>/gui/setup-token` (0600) on first start, never logged;
   `central gui reset-admin` prints a new one for recovery (§2.3).
5. **Sessions in SQLite (changed by the user)** [draft: in memory]: table `gui_sessions` in
   migration 0003, only `SHA-256(token)` stored, CSRF key derived from the cookie so a DB copy
   cannot hijack, idle 30 min / absolute 12 h, bound to the credential generation (password change
   or `reset-admin` kills sessions at once, in the same transaction), passive polling never
   extends, expired rows purged at start and every 10 min, sessions survive a restart (§2.4, §2.9;
   tested in §6.1 steps 11–12, S14, §6.2).
6. **Fleet guard toggle: yes.** `service.SetFleetConfirm`, admin method `fleet.set_confirm`,
   `central fleet set NAME -confirm=BOOL`, GUI toggle; turning it off needs the typed fleet name.
7. **No actions from the GUI.** `central exec` stays; the runner detail shows advertised actions
   read-only.
8. **Audit filtering: `Store.QueryAudit`** with keyset paging, two new indexes, `service.ListAudit`,
   same filters on `central audit`.
9. **htmx: latest 2.0.x, pinned by SHA-256.** htmx 4.0 revisited after it becomes npm `latest`.
10. **Fonts embedded:** Oswald and JetBrains Mono woff2 with their OFL texts.
11. **GUI on by default at `0.0.0.0:8443` (changed by the user)** [draft: `127.0.0.1:8443`], with
    the self-signed certificate when no `-gui-cert/-gui-key` is given. Consequences planned here:
    startup notice (all interfaces, how to restrict: `-gui-listen 127.0.0.1:8443`, `off`, firewall;
    the fingerprint), a Host allowlist that still blocks DNS rebinding (own interface IPs, hostname,
    `localhost`, `-gui-host`, exact match; §2.2), and a re-checked setup flow for a LAN-reachable
    `/setup` (§2.3). `-gui-listen off` disables the GUI.
12. **Screenshots: yes**, `scripts/dev.sh gui-shots` with a digest-pinned headless Chromium
    container, outside the gate (S16).

**ETA:** ~26 h agent time, ~8.5 h wall-clock over waves A–E plus 5 reviews (~10.5 h total). The
user's changes add about 2 h of agent time (session store, Host allowlist, extra tests).
