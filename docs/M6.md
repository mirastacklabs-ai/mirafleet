# M6 — Release and distribution: implementation plan

Parent: [PLAN.md](PLAN.md) M6 (channel tables, cross-platform rules). Design:
[ARCHITECTURE.md](ARCHITECTURE.md). Inputs: [M5.md](M5.md) (deferred F-45, F-47, F-48; the
`integrations/` layout), [M4.md](M4.md) (Admin GUI: flag names, setup token, defaults),
[M7.md](M7.md) (remote development on a VM; its §11 lists what M6 must ship).

**Status: approved 14 Nov 2026; re-planned the same day to run in parallel with M4 and M7.**
Completion order stays **M4 → M7 → M6**: v0.6.0 ships the GUI, host mode, credentials and the
parity tools. M6 work starts now in its own git worktree, in two lanes (§5):
- **Now lane:** steps that touch no file M4 or M7 will change. Start immediately.
- **Late lane:** steps that need M4's or M7's final names (GUI flags, host-mode units, secrets
  key, quickstart, threat model, plugin bump, version-skew wiring). They start when M4, then M7, land.
- **Publish:** outward-facing steps last; each needs the user's explicit yes at that moment (§8).

M5 is done; its smoke test (M5 S17) runs in the user's full-product test (L9).

Decisions are in §10 (Q1–Q22). One question is still open: **Q23**, whether the docs list Docker
Hub or ghcr first. The recommendation is Docker Hub first.

Goal: when M6 is complete, the whole platform installs end to end from release artifacts.
- Central and runners on Linux: packages, the OCI image (Docker Hub and ghcr), Docker Compose and
  `install.sh`.
- `mirafleet mcp` on macOS, Linux and Windows: archives, Homebrew, npm, `install.sh`/`install.ps1`.
- The Claude Code plugin from the marketplace, plus tested MCP configs for eight other harnesses.
- A first-run quickstart covering the GUI bootstrap and remote development on a VM.

Process as in M5: each step keeps `scripts/dev.sh fmt|build|vet|test|cross|licenses` green; scoped
checks while iterating, the full gate once; one qa-reviewer per wave; only P0/P1 are fixed before
merge; P2/P3 go to the G6-xx list at the end, fixed in L9.

Changes land through a short-lived branch, a PR, and auto-merge once CI is green; the branch is
deleted after merge (§2.19). Steps in a wave touch disjoint files. In the now lane `scripts/dev.sh`
is **not** touched (M4 and M7 edit it); M6 tooling lives in a new `scripts/release.sh`, and only
one step per wave edits it. No new Go module. Every brief repeats: no host tools; at most one
background waiter per long run, and it must also exit on failure or when the job dies; do not touch
M4/M7 files.

Worktree rules (parallel milestones):
- M6 works in `../mirafleet-m6` (`git worktree add`), one branch per step (`m6/<step-id>`).
- `scripts/dev.sh integration` uses the shared `mirafleet-itest-bin` volume, so only one
  integration run may happen at a time across all worktrees. The now lane relies on CI for it.
- Disk is low: `scripts/release.sh clean` removes `dist/`, test images and volumes after each
  wave, and the worktree is removed when M6 is merged.

## 2. Design decisions

### 2.1 One tag, one version, every channel
- The version is the git tag `vX.Y.Z` (semver; pre-releases `vX.Y.Z-rc.N`). First release **v0.6.0** (Q1).
- One commit before the tag bumps every versioned file together:
  - `integrations/claude-code/.claude-plugin/plugin.json`;
  - `pluginVersion` in `cmd/mirafleet/mcp_hook.go` (the plugin bump; it ships M7's skill and hook changes);
  - the plugin entry `ref` in `.claude-plugin/marketplace.json`;
  - `server.json`.

  npm templates carry no version.
- `tools/relgen` does `bump X.Y.Z` and `check vX.Y.Z`. The release workflow runs `check` against
  the tag and stops on any mismatch.
- Binary version: goreleaser sets `-X main.version={{.Version}}`. A new file
  `cmd/mirafleet/version_buildinfo.go` adds an `init()` that, when `version == "dev"`, uses
  `debug.ReadBuildInfo().Main.Version` (not `(devel)`), so `go install …@v0.6.0` prints `v0.6.0`.
  It is a new file, so `main.go` (changed by M4 and M7) is not touched. No `version -v`;
  `go version -m` shows commit and build settings.

### 2.2 Protocol version and skew (Q14)
- One integer **protocol level** = the release's minor version while in 0.x (v0.6.x → 6), in a new
  package `internal/protover` (`Current`, `Check(role, central, peer int) error`). From 1.0 it
  follows the major version; the rule is documented in the package.
- **Rule:** central at level N accepts runners and orchestrators at N and N−1. Anything else is
  refused with a message that names who must upgrade:
  - peer < N−1: "runner `db-1` is protocol 4, central needs 5 or 6: upgrade mirafleet on that runner";
  - peer > N: "central is protocol 6, this runner is 7: upgrade central first".

  Upgrade order, documented: central first, then runners, then operators.
- **Wiring** (late lane, after M7 lands; it touches `api`, `transport`, `central`, `runner`, `orch`):
  - Runners: the heartbeat gains `proto` (additive). Central checks it on the first heartbeat and,
    on a mismatch, sends `refused@mirafleet` with the message, audits `runner.refused_version` and
    closes. The runner logs the message and backs off to its maximum interval (no fast reconnect loop).
  - Operators: `hello` gains `proto` in params and result. `orch` maps a refusal to a tool error
    (setup-error style) with the same message. `mcp login` prints it.
  - A missing `proto` (pre-0.6 dev builds) counts as level 0, which is refused.
- Tests: a `Check` table (N/N, N/N−1 accepted; N/N−2 and N/N+1 refused with the exact texts);
  in-process central with a runner and an orchestrator faking levels (refused, audited, message
  delivered, runner backoff on an injected clock); `TestM5NoHooks` still passes at level N.

### 2.3 Upgrades: SQLite backup before migrations (Q15)
- In `internal/store/sqlite` (new `backup.go`, small change in `migrate.go`; neither M4 nor M7
  changes these, M7 only adds a migration file):
  - Before the migration transaction, read `user_version`. If 0 < current < latest, run
    `VACUUM INTO '<datadir>/backups/mirafleet-schema<cur>-<UTC yyyymmddThhmmssZ>.db'` (an online,
    consistent copy). Dir 0700, file 0600 (central's umask is 077).
  - Then migrate as today. Keep the **3 newest** backups and prune older ones, only after a
    successful migration.
  - If the backup fails (disk full, permissions), central does **not** migrate and refuses to
    start with a clear error.
  - A database newer than the binary is already refused (`migrate.go`). The test pins the message,
    which tells the admin to install the newer binary or restore a backup.
- Rollback (RELEASING.md and guide ch. 10):
  1. Stop central.
  2. Reinstall the previous version.
  3. Move `mirafleet.db`, `-wal` and `-shm` aside.
  4. Copy the newest `backups/…schema<N>…` back as `mirafleet.db`.
  5. Start central.

  Writes made after the upgrade are lost; the docs say so.
- Backups hold M7's credentials as encrypted as the database does: they are useless without
  `MIRAFLEET_SECRETS_KEY`, and so is a restore.
- Tests: a fresh DB makes no backup; an upgrade from a schema-1 DB writes a backup whose
  `user_version` is 1 and whose rows match; four upgrades keep 3; a failed backup (read-only backups
  dir) leaves the DB untouched and returns the error; a newer DB is refused with the pinned text;
  a restore round trip works.

### 2.4 goreleaser (OSS only) builds; our jobs publish
- goreleaser OSS v2 (MIT), pinned by version and image digest. It never uses Pro features: the npm
  publisher, split/merge, `token_type`.
- goreleaser does the builds, archives, nFPM packages, `checksums.txt`, SBOMs (syft), cosign
  keyless `sign-blob` of `checksums.txt`, and a **draft** GitHub release.
- It does **not** push images, Homebrew or npm. Those are separate, separately approved jobs (§2.16).
  The deprecated `brews` and `dockers` sections are not used.
- Builds: `CGO_ENABLED=0`, `-trimpath`, `-ldflags "-s -w -X main.version={{.Version}}"`,
  `mod_timestamp: {{.CommitTimestamp}}`, `-buildvcs=false`. Targets: the six from
  `scripts/dev.sh TARGETS` (a relgen check compares them).
- Archives: `mirafleet_<ver>_<os>_<arch>.tar.gz` (zip on Windows), each with the binary, `LICENSE`,
  `NOTICE`, `THIRD_PARTY_LICENSES.txt`, `README.md` and `QUICKSTART.md`.
- Tools image: `scripts/release/tools.Dockerfile` = the pinned goreleaser image plus `syft` and
  `cosign` copied from their pinned images. It is built by `scripts/release.sh snapshot`.

### 2.5 Linux packages (nFPM)
Package `mirafleet`, amd64/arm64.

| Path | Mode / owner | deb, rpm | apk | Lane |
|---|---|---|---|---|
| `/usr/bin/mirafleet` | 0755 root | yes | yes | now |
| `/usr/lib/systemd/system/mirafleet-central.service` | 0644 | yes | no | now |
| `/usr/lib/systemd/system/mirafleet-runner.service` (actions mode) | 0644 | yes | no | now |
| `/usr/lib/systemd/system/mirafleet-runner-workspace.service` (container workspaces, root) | 0644 | yes | no | now |
| `/usr/lib/systemd/user/mirafleet-runner.service` (M7 host mode, user unit) | 0644 | yes | no | late (M7 creates the file) |
| `/usr/lib/systemd/system/mirafleet-runner@.service` (M7 host mode, `User=%i`) | 0644 | yes | no | late (M7 creates the file) |
| `/etc/mirafleet/central.env` | **0600 root**, config noreplace | yes | yes | now (secrets line late) |
| `/etc/mirafleet/runner.env` | 0644, config noreplace | yes | yes | now |
| `/usr/share/doc/mirafleet/{LICENSE,NOTICE,THIRD_PARTY_LICENSES.txt,QUICKSTART.md}` | 0644 | yes | yes | now |
| `/usr/share/doc/mirafleet/examples/{actions.yaml,workspace.yaml}` | 0644 | yes | yes | now |
| `/usr/share/doc/mirafleet/examples/workspace-host.yaml` | 0644 | yes | yes | late (M7) |

- No live `actions.yaml`/`workspace.yaml` is installed; the runner refuses to start without one.
- Packages create **no runner users**. Host mode users are the admin's step: `useradd -m dev`,
  `loginctl enable-linger dev`, and the same for a second runner `qa` (quickstart).
- Maintainer scripts (POSIX sh, one set, `set -eu`, idempotent):
  - preinstall: create group and system user `mirafleet` (home `/var/lib/mirafleet`, nologin) if absent.
  - postinstall:
    - `install -d -m 0700 -o mirafleet -g mirafleet /var/lib/mirafleet/{central,runner}`;
    - `install -d -m 0700 -o root /var/lib/mirafleet/runner-ws`;
    - `daemon-reload` when systemd runs;
    - on upgrade, `try-restart` the system units. Migrations then run with the automatic backup.
    - Units are not enabled on first install.
    - Prints the firewall note (below).
  - preremove (removal only, not upgrade): `systemctl disable --now` the system units.
  - postremove: `daemon-reload`.
  - The scripts **never** delete `/var/lib/mirafleet` or any user, also on purge.
- `central.env` (0600 root; systemd reads it before dropping to `mirafleet`):
  - Now lane: `MIRAFLEET_LISTEN=0.0.0.0:2222`, `MIRAFLEET_CENTRAL_ARGS=`, and commented GUI lines
    using M4.md's flags: `-gui-listen` (default `0.0.0.0:8443`, `127.0.0.1:8443`, or `off`),
    `-gui-cert`/`-gui-key`, `-gui-host`, `-advertise`.
  - Late lane: `MIRAFLEET_SECRETS_KEY=` with the comment "generate with
    `mirafleet central keygen`; losing it loses every stored credential; back it up apart
    from the data dir" (names from M7.md, checked against the landed code). Also a commented
    optional corporate CA file line (variable name as in M7.md), needed only for GitLab token
    self-rotation.
- **Firewall note** (env file, postinstall message, quickstart): 2222 must reach runners and
  operators. The GUI listens on all interfaces by default, so allow 8443 only from admins'
  networks, or use `-gui-listen 127.0.0.1:8443` with `ssh -L`. Central needs no outbound access,
  except HTTPS to GitLab when token self-rotation (M7) is used. The scratch image has no CA
  bundle, so in the image that case needs the CA file mounted read-only. The packages do not
  change the firewall.

### 2.6 systemd units (Q10)
- `mirafleet-central.service`:
  - `User=mirafleet`, `EnvironmentFile=/etc/mirafleet/central.env`.
  - `ExecStartPre=/usr/bin/mirafleet central init -data /var/lib/mirafleet/central` (idempotent;
    no new code, so `central_linux.go` stays untouched).
  - `ExecStart=/usr/bin/mirafleet central run -data /var/lib/mirafleet/central -listen ${MIRAFLEET_LISTEN} $MIRAFLEET_CENTRAL_ARGS`.
  - `Restart=on-failure`, `UMask=0077`.
  - Strict sandbox: `NoNewPrivileges`, `ProtectSystem=strict`,
    `ReadWritePaths=/var/lib/mirafleet/central` (database, backups, GUI cert, setup-token file,
    admin socket), `ProtectHome`, `PrivateTmp`, `PrivateDevices`, `ProtectKernel{Tunables,Modules,Logs}`,
    `ProtectControlGroups`, `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6`, `RestrictNamespaces`,
    `LockPersonality`, `MemoryDenyWriteExecute`, `SystemCallArchitectures=native`,
    `SystemCallFilter=@system-service`, an empty `CapabilityBoundingSet=`.
  - Port < 1024 needs a documented drop-in adding `CAP_NET_BIND_SERVICE`.
- Admin commands run as the unit user (the admin socket checks the peer UID):
  `sudo -u mirafleet mirafleet central …`.
- `mirafleet-runner.service` (actions):
  - `User=mirafleet`, `ConditionPathExists=/var/lib/mirafleet/runner/runner.yaml`, `-actions /etc/mirafleet/actions.yaml`.
  - Light sandbox only (`PrivateTmp`, `ProtectKernelModules`, `RestrictAddressFamilies`); a strict
    drop-in example is in the docs.
- `mirafleet-runner-workspace.service` (container workspaces):
  - `User=root`, data dir `/var/lib/mirafleet/runner-ws`, `After=/Wants=containerd.service`.
  - No sandbox directives (the runner creates namespaces and cgroups).
- M7's host-mode units (`KillMode=process`) are packaged as M7 wrote them. In the package test,
  `pkgtest` runs `systemd-analyze verify` on all five units, and on the user unit with `--user`.

### 2.7 OCI image, two registries (Q16, Q23)
- `packaging/oci/Dockerfile`:
  - `FROM scratch`; `COPY` the static binary to `/usr/bin/mirafleet` and the licence files to `/usr/share/doc/mirafleet/`.
  - `USER 65532:65532`, `ENV HOME=/var/lib/mirafleet`, `VOLUME /var/lib/mirafleet`, `EXPOSE 2222 8443`.
  - `ENTRYPOINT ["/usr/bin/mirafleet"]`, `CMD ["central","run","-data","/var/lib/mirafleet/central","-listen","0.0.0.0:2222"]`.
  - Only `COPY` lines, so buildx builds both architectures without QEMU.
  - Not distroless: it ships `ca-certificates` (MPL-2.0), which may not be bundled.
- First start needs `central init`. Compose does it in a one-shot `central-init` service, which
  `central` waits on with `depends_on: condition: service_completed_successfully`. With plain
  `docker run`, the docs show two commands: `… central init`, then `… central run …`.
- Labels: OCI `org.opencontainers.image.{source,version,revision,licenses,title,description}`.
- **One build, two registries, same digest:** buildx pushes one multi-arch manifest to
  `docker.io/mirastack/mirafleet` and `ghcr.io/mirastacklabs-ai/mirafleet`. Then `cosign sign` and
  a provenance attestation for each repository, by digest.
- Tags: `X.Y.Z`, `X.Y`, `latest` (pre-releases get only `X.Y.Z-rc.N`).
- Admin: `docker exec <c> mirafleet central …` (same UID). There is no shell, so the setup token
  is read with `docker cp <c>:/var/lib/mirafleet/central/<setup-token file from M4.md> -` (tar
  stream) or `docker compose cp` (late step L1 confirms the file name, or a CLI to print it if
  M4 adds one).
- GUI: on by default at `0.0.0.0:8443` in the container. The self-signed certificate lives in the
  volume, so its fingerprint survives restarts. The docs publish `-p 127.0.0.1:8443:8443` by
  default and show a real cert mounted read-only with `-gui-cert`/`-gui-key`. No cert, key or
  secrets key is baked into the image. M7's `MIRAFLEET_SECRETS_KEY` comes from an `--env-file`
  (0600) (late).
- The image also runs an **actions-mode runner** (`runner join`, `runner run -actions …`). Container
  workspaces and host mode are not supported in the image: they need host containerd or a real OS user.

### 2.8 Docker Compose (first-class install)
- `deploy/compose/`:
  - `central/compose.yaml`: `central-init` + `central`; named volume; ports `2222:2222`;
    `127.0.0.1:8443:8443` by default, with a comment showing how to open it wider; `env_file: central.env` (late adds the secrets key).
  - `runner/compose.yaml`: one actions runner with `actions.yaml` mounted read-only. Join is a
    one-shot `docker compose run --rm runner runner join … -token -`.
  - `lab/compose.yaml`: central + runner + an operator container on one machine (the try-it lab and test).
  - `README.md` for each.
- Image references in the files use the registry chosen in Q23, pinned to `:0.6.0` (relgen bumps them).
- Restart policy `unless-stopped`. Kept simple: no extra hardening options beyond the image's
  non-root user (the user's standing preference).

### 2.9 npm wrapper `@mirastacklabs/mirafleet` (Q4)
- `relgen npm` generates seven packages from the release archives:
  - the wrapper `bin/mirafleet.js`: no dependencies, exact `optionalDependencies`, `mcpName`, `engines.node >= 18`;
  - six platform packages (`os`/`cpu`, the binary and the licence files).
- No lifecycle scripts, no download.
- The launcher resolves the platform package, `spawn`s with `stdio: "inherit"`, forwards
  signals, and exits with the child's code. It names the package when one is missing and never
  writes to stdout.
- Use it as `npx -y @mirastacklabs/mirafleet@0.6.0 mcp -project-dir .`; on Windows, `cmd /c npx …`
  where the harness spawns without a shell.
- Not for the Claude Code plugin on Windows: the `.cmd` shim cannot run exec-form hooks (Q9).
- Publish with `npm publish --provenance --access public` via trusted publishing.

### 2.10 Homebrew tap (Q3)
- `Formula/mirafleet.rb` is rendered by `relgen brew` from `checksums.txt`, with `on_macos`/`on_linux` × arch blocks.
- `test do` runs `mirafleet version`.
- It is pushed by the `brew` job with `HOMEBREW_TAP_TOKEN` and skipped for pre-releases.

### 2.11 `install.sh` and `install.ps1` (Q7, Q9)
- `scripts/install.sh` (POSIX, shellcheck clean):
  - linux/darwin, amd64/arm64; `-v vX.Y.Z` or latest (from the `releases/latest` redirect); `-b DIR`.
  - HTTPS only. **SHA-256 always verified**; it refuses if no sha256 tool exists, if the archive is
    not listed, or on a mismatch. It extracts only the binary, never runs `sudo`, and cleans its
    temp dir.
  - It verifies the cosign signature of `checksums.txt` when `cosign` is present, and requires it
    with `--verify-signature`, using the exact workflow identity and the GitHub OIDC issuer.
  - `MIRAFLEET_INSTALL_BASE_URL` (tests and the lab) points at a `file://` dist.
- `scripts/install.ps1` (PowerShell 5.1 and 7): the same flow; installs to
  `%LocalAppData%\Programs\mirafleet\mirafleet.exe`; changes the user PATH only with `-AddToPath`; never needs admin.
- No Apple notarization or Microsoft code signing. The docs say that brew, npm, `install.sh` and
  `install.ps1` are not affected by quarantine. For a zip downloaded in a browser, after the
  checksum check:
  - macOS: `xattr -d com.apple.quarantine mirafleet`;
  - Windows: `Unblock-File .\mirafleet.exe`, or Properties → Unblock (best done on the zip).

### 2.12 `tools/relgen` (stdlib only)
`package main` under `tools/relgen/`, never linked into `mirafleet`. Each subcommand is in its own
file and registers itself in `init()`, so parallel steps never share a file:
- `check`/`bump`: versions, targets, marketplace `ref`, compose image tags;
- `licenses`;
- `npm`;
- `brew`;
- `serverjson`;
- `wiki`: docs → wiki pages, below;
- `harness`: checks that every harness command copy equals `integrations/commands/mirafleet.md`.

Golden-file tests for each. Run via `scripts/dev.sh go run ./tools/relgen …`.

### 2.13 Third-party licences

- `licenses/extra/` covers, reviewed by hand:
  - `modernc.org/mathutil`, `segmentio/asm`, the musl notice in `modernc.org/libc`;

- A relgen test ties `licenses/extra/` to the `--ignore`s in dev.sh and to `ASSETS.md`.

### 2.15 CI (`ci.yml`, `orchestrator.yml`, `dco.yml`)
- `pull_request` and `push` to main. `permissions: contents: read`; no secrets; never
  `pull_request_target`. Actions pinned by commit SHA (reuse the existing pins; resolve new ones
  with `gh api`). `persist-credentials: false`.
- `ci.yml` jobs (ubuntu-latest, through `scripts/dev.sh` and `scripts/release.sh`):
  - `gate`, `licenses`, `vuln`, `lint`;
  - `integration`: the privileged harness. Once M7 lands it includes the two-user host-mode test;
    no CI change is needed, because `dev.sh integration` carries it.

## 3. First-run quickstart (`docs/QUICKSTART.md`, late, also in every archive)
It uses the guide's running example. Each part ends with a "check it worked" line.
1. **Central (Linux): package, Compose or image.**
   - Firewall first: 2222 for runners and operators; 8443 for admins only, or `-gui-listen 127.0.0.1:8443`.
   - Generate the secrets key (`mirafleet central keygen`) into `/etc/mirafleet/central.env`
     (0600 root, or Compose's env file). Back it up apart from the data.
   - `systemctl enable --now mirafleet-central`.
   - The journal shows the SSH host-key fingerprint, the GUI URLs, the GUI certificate fingerprint,
     the all-interfaces notice and the **path** of the setup-token file. Wording follows M4.md.
   - Admin commands as `sudo -u mirafleet mirafleet central …`.
2. **GUI bootstrap.**
   1. Open `https://central.example.com:8443` (or tunnel with `ssh -L`).
   2. Compare the browser's certificate fingerprint with the journal and continue only if they match.
   3. Read the token with `sudo -u mirafleet cat <path>` (Compose: `docker compose cp`).
   4. Create the admin; sessions survive restarts.
   5. Create fleet `dev` and a join token.
3. **Runner (Linux).** Actions runner: package, example `actions.yaml`, join as `mirafleet`,
   `mirafleet-runner`, approve. Container-workspace variant (root, containerd). Compose variant.
4. **Remote development on a VM (M7).**
   1. `useradd -m dev`, `loginctl enable-linger dev`, then as `dev`: `mirafleet runner join … -name vm1-dev -token -`.
   2. Copy `workspace-host.yaml`, then `systemctl --user enable --now mirafleet-runner` (the
      user unit, shown first). The alternative is the system unit `mirafleet-runner@dev`.
   3. The VM firewall is the egress control.
   4. Credentials page: a GitLab deploy key with write access, a project access token with
      `write_repository`, a registry token. Assign them to the runner.
   5. `.mirafleet.yaml` `remote: true`; then the Claude Code loop.
   6. **Add a second runner**: user `qa` (or another VM), enrolled and assigned separately.

   A runner serves one operator at a time, and any operator may use any runner, so each
   developer gets their own runner user. Token self-rotation needs outbound HTTPS from central
   to GitLab.
5. **Operator (macOS, Linux, Windows).** brew / `install.sh` / `install.ps1` / npm; `mcp login`.
   Claude Code marketplace install; other harnesses via `integrations/<harness>/`.
6. **Upgrade and rollback** (§2.2 order, §2.3 backup), **uninstall** (data kept), the **quarantine
   one-liners**, the **test lab** (a separate colima profile from snapshot artifacts, never the
   dev profile), and **one-machine try-it** (`deploy/compose/lab`).

## 13. Risks

| Risk | Mitigation |
|---|---|
| Parallel lanes collide on a file | the now lane's files are listed per step and exclude every M4/M7 file; `scripts/release.sh` instead of dev.sh; reviewers check the diff against the list |
| F-47/F-48 merge late and conflict with M7 wave B | N1.4 is first in the queue; the M7 brief says to rebase on it |
| Shared `mirafleet-itest-bin` volume across worktrees | one integration run at a time; the now lane relies on CI |
| M4/M7 names change after N2 | late steps L1/L3 re-check every name against the landed code; tests use the flags |
| goreleaser OSS churn | pin; minimal feature set |
| npm trusted publishing rules / burned versions | `NPM_TOKEN` fallback once; rc to `next` first |
| Windows `.cmd` shim; browser quarantine | `install.ps1` + zip; one-liners after the checksum check |
| GUI exposed on all interfaces with a self-signed cert | firewall note everywhere; fingerprint check; `127.0.0.1` in Compose by default |
| Secrets key lost or leaked | quickstart warning, 0600 root env file, backup apart; THREAT-MODEL |
| Accepted host-mode enrolment-key gap | documented in THREAT-MODEL and the quickstart; duplicate-login refusal and audit |
| Backup fills the disk | VACUUM INTO fails → no migration, clear error; keep 3 |
| Skew refusal locks out a fleet mid-upgrade | documented order (central first); N−1 accepted |
| Harness config formats drift | dated doc URLs; `harnesscheck` where a CLI exists; user check |
| Wrong commit tagged | `verify` job; tag ruleset |
| Low disk | `release.sh clean` after each wave; worktree removed at the end |
