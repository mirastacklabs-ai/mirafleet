# M6 — Release and distribution: implementation plan

Parent: [PLAN.md](PLAN.md) M6 (channel tables, cross-platform rules). Design:
[ARCHITECTURE.md](ARCHITECTURE.md). Inputs: [M5.md](M5.md) (deferred F-45, F-47, F-48; the
`integrations/` layout), M4.md (Admin GUI, written in parallel; M6 is built after M4).

**Status: approved 14 Nov 2026.** Decisions on §10: Q1 first version v0.6.0; Q2 tools that run
only in containers or CI and never ship may sit outside the allowlist (CLAUDE.md); Q3 Homebrew
formula generated by relgen; Q4 npm `@mirastacklabs`, registry `io.github.mirastacklabs-ai/mirafleet`;
Q5 `server.json` lists npm only; Q6 marketplace `mirastacklabs`, pinned to the release tag; Q7 no
macOS notarization or Windows code signing (dropped, not deferred; cosign and checksums stay);
Q8 `v0.6.0-rc.1` rehearsal first; Q9 Windows via `install.ps1` + zip; Q10 central strict, actions
runner light, workspace runner none. From M4: the GUI is on by default at `0.0.0.0:8443` with a
self-signed certificate unless `-gui-cert`/`-gui-key` are given, sessions in SQLite (exact flag
names: [M4.md](M4.md)). Built after M4. M5's user smoke test (M5 S17) should be done first.

Goal: when M6 is built, the whole platform installs end to end from release artifacts: central
and runners on Linux (packages, OCI image, `install.sh`), `mirafleet mcp` on macOS, Linux and
Windows (archives, Homebrew, npm, `install.sh`/`install.ps1`), the Claude Code plugin from the
marketplace, and a first-run quickstart that covers the GUI bootstrap. Everything is built and
checked locally and in CI first. Publishing (tag, GitHub release, ghcr, npm, Homebrew tap, MCP
Registry, plugin directory, galleries) is a separate, last stage; **every outward-facing step
needs the user's explicit confirmation at the time it runs** (§8).

Process as in M5: every step keeps `scripts/dev.sh fmt|build|vet|test|cross|licenses` green;
agents run scoped checks while iterating and the full gate once; one qa-reviewer per wave; only
P0/P1 are fixed before a push; P2/P3 go to a G-xx list at the end of this file, fixed in wave E.
Parallel agents share one worktree; steps in a wave touch disjoint files; only one step per wave
touches `scripts/dev.sh` (named in the table). No new Go module dependencies in M6.

## 2. Design decisions

### 2.1 One tag, one version, every channel
- The version is the git tag `vX.Y.Z` (semver; pre-releases `vX.Y.Z-rc.N`). First release
  **v0.6.0** (Q1): the plugin is already 0.5.0, versions must only grow.
- Files that carry the version are checked in and bumped together by one commit before the
  tag: `integrations/claude-code/.claude-plugin/plugin.json`, `pluginVersion` in
  `cmd/mirafleet/mcp_hook.go`, the plugin entry `ref` in `.claude-plugin/marketplace.json`,
  `server.json` (`version` and package versions). The npm templates carry no version; it is
  filled in at release from the tag.
- `tools/relgen` (§2.9) does `bump X.Y.Z` and `check vX.Y.Z`. The release workflow runs `check`
  against the pushed tag and stops on any mismatch.
- Binary version: goreleaser sets `-X main.version={{.Version}}`. When `version == "dev"`,
  `main` falls back to `debug.ReadBuildInfo().Main.Version` (not `(devel)`), so
  `go install …/cmd/mirafleet@v0.6.0` prints `v0.6.0`. `mirafleet version -v` adds commit, build
  date, Go version and `GOOS/GOARCH` (from build info).

### 2.2 goreleaser (OSS only) builds; our own jobs publish
- goreleaser OSS v2 (MIT), pinned by version and image digest. Pro features are never used
  (npm publisher, split/merge, `token_type`). goreleaser's npm publisher is Pro-only and uses a
  `postinstall` download, which PLAN rejects, so npm is ours (§2.6).
- goreleaser does: builds, archives, nFPM packages, `checksums.txt`, SBOMs (syft), cosign
  keyless `sign-blob` of `checksums.txt`, and a **draft** GitHub release with changelog. It does
  **not** push images, Homebrew or npm: those are separate, separately approved jobs (§7), so each
  outward step is its own confirmation point. Deprecated sections (`brews`, `dockers`) are not used.
- Builds: `CGO_ENABLED=0`, `-trimpath`, `-ldflags "-s -w -X main.version=… -X main.commit=… -X main.date=…"`,
  `mod_timestamp: {{.CommitTimestamp}}` (reproducible), `flags: -buildvcs=false` as in dev.sh.
- Targets: linux/darwin/windows × amd64/arm64 (same list as `scripts/dev.sh TARGETS`; a relgen
  test checks the two agree).
- Archives: `mirafleet_<ver>_<os>_<arch>.tar.gz` (zip on Windows), each with the binary,
  `LICENSE`, `NOTICE`, `THIRD_PARTY_LICENSES.txt`, `README.md`, `QUICKSTART.md`.
- Tools image: `scripts/release/tools.Dockerfile` = pinned goreleaser image plus `syft` and
  `cosign` binaries copied from their pinned images (`COPY --from=…@sha256:…`). Built locally by
  `scripts/dev.sh release-snapshot`; nothing is installed on the host.

### 2.3 Linux packages (nFPM through goreleaser)
Package `mirafleet`, arch amd64/arm64 (`x86_64`/`aarch64` for rpm/apk). Contents:

| Path | Mode / owner | deb, rpm | apk |
|---|---|---|---|
| `/usr/bin/mirafleet` | 0755 root | yes | yes |
| `/usr/lib/systemd/system/mirafleet-central.service` | 0644 | yes | no |
| `/usr/lib/systemd/system/mirafleet-runner.service` (actions mode) | 0644 | yes | no |
| `/usr/lib/systemd/system/mirafleet-runner-workspace.service` (workspace mode) | 0644 | yes | no |
| `/etc/mirafleet/central.env`, `/etc/mirafleet/runner.env` | 0644, config (noreplace) | yes | yes |
| `/usr/share/doc/mirafleet/{LICENSE,NOTICE,THIRD_PARTY_LICENSES.txt,QUICKSTART.md}` | 0644 | yes | yes |
| `/usr/share/doc/mirafleet/examples/{actions.yaml,workspace.yaml}` | 0644 | yes | yes |

- No live `actions.yaml`/`workspace.yaml` is installed: the runner refuses to start without one,
  which is the safe default. The admin copies an example and edits it.
- Scripts (POSIX sh, one set, branch on `command -v useradd`/`adduser`):
  - preinstall: create group and system user `mirafleet` (home `/var/lib/mirafleet`, shell
    `/usr/sbin/nologin` or `/sbin/nologin`), only if absent.
  - postinstall: `install -d -m 0700 -o mirafleet -g mirafleet /var/lib/mirafleet/central
    /var/lib/mirafleet/runner`; `install -d -m 0700 -o root /var/lib/mirafleet/runner-ws`;
    `systemctl daemon-reload` when systemd is running; on **upgrade** `systemctl try-restart` of the
    three units (only those already running; migrations run on start). Units are **not** enabled or
    started on first install.
  - preremove (removal only, not upgrade): `systemctl disable --now` the three units.
  - postremove: `daemon-reload`. **Never** deletes `/var/lib/mirafleet` or the user, also on
    `purge`; prints where the data is. Deleting keys and the database is the admin's call.
- `central.env`: `MIRAFLEET_LISTEN=0.0.0.0:2222`, `MIRAFLEET_CENTRAL_ARGS=` (empty: the GUI then
  runs with M4's defaults, `0.0.0.0:8443`, self-signed certificate). Commented lines show the GUI
  flags from M4.md: listen address (for example `127.0.0.1:8443` to keep it local-only),
  `-gui-cert`/`-gui-key` for a real certificate (files readable by `mirafleet`, for example under
  `/etc/mirafleet/tls/`), and how to turn the GUI off if M4 offers that. `runner.env`:
  `MIRAFLEET_RUNNER_ARGS=`.
- **Firewall note** (in `central.env`, the postinstall message and the quickstart): the GUI listens
  on every interface by default. Allow 8443 only from the admins' network, or bind it to
  `127.0.0.1` and use `ssh -L`. 2222 must be reachable by runners and operators. The packages do
  not change the firewall.

### 2.4 systemd units
- `mirafleet-central.service`: `User=mirafleet`, `EnvironmentFile=/etc/mirafleet/central.env`,
  `ExecStart=/usr/bin/mirafleet central run -init -data /var/lib/mirafleet/central -listen ${MIRAFLEET_LISTEN} $MIRAFLEET_CENTRAL_ARGS`,
  `Restart=on-failure`, `UMask=0077`, and strict sandboxing: `NoNewPrivileges`, `ProtectSystem=strict`,
  `ReadWritePaths=/var/lib/mirafleet/central`, `ProtectHome`, `PrivateTmp`, `PrivateDevices`,
  `ProtectKernel{Tunables,Modules,Logs}`, `ProtectControlGroups`, `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6`,
  `RestrictNamespaces`, `LockPersonality`, `MemoryDenyWriteExecute`, `SystemCallArchitectures=native`,
  `SystemCallFilter=@system-service`, `CapabilityBoundingSet=` (empty). Port < 1024 (443 in
  internet mode) is a documented drop-in adding `CAP_NET_BIND_SERVICE` (ambient and bounding).
  The GUI needs nothing extra: its self-signed certificate and its sessions live in the data dir
  (SQLite), which is the one writable path; `-gui-cert`/`-gui-key` files are read-only.
- `central run -init` (new flag, step R0) runs the existing idempotent `central init` first. It
  replaces an `ExecStartPre` and is what the OCI image needs (no shell in a scratch image).
- Admin commands run as the unit's user because the admin socket checks the peer UID:
  `sudo -u mirafleet mirafleet central fleet list`. The quickstart says so up front.
- `mirafleet-runner.service` (actions mode): `User=mirafleet`,
  `ConditionPathExists=/var/lib/mirafleet/runner/runner.yaml` (no crash loop before `join`),
  `ExecStart=/usr/bin/mirafleet runner run -data /var/lib/mirafleet/runner -actions /etc/mirafleet/actions.yaml $MIRAFLEET_RUNNER_ARGS`.
  **Light** sandboxing only (`PrivateTmp`, `ProtectKernelModules`, `RestrictAddressFamilies`):
  actions are admin-defined commands (they may need `sudo` or to write files), so
  `NoNewPrivileges`/`ProtectSystem` would break them in surprising ways. A commented strict
  drop-in example ships in the docs.
- `mirafleet-runner-workspace.service`: `User=root` (containerd socket; the runner is
  root-equivalent anyway, ARCHITECTURE), data dir `/var/lib/mirafleet/runner-ws`,
  `-workspace /etc/mirafleet/workspace.yaml`, `After=containerd.service`, `Wants=containerd.service`,
  no sandbox directives (it creates namespaces and cgroups). `Conflicts=` is not set: one host may
  run both, with separate data dirs.
- `systemd-analyze verify` runs on all three in the package test (§2.11).

### 2.5 OCI image `ghcr.io/mirastacklabs-ai/mirafleet`
- `packaging/oci/Dockerfile`: `FROM scratch`; `COPY` the static linux binary to
  `/usr/bin/mirafleet` (0755) and the licence files to `/usr/share/doc/mirafleet/`; `USER 65532:65532`;
  `ENV HOME=/var/lib/mirafleet`; `VOLUME /var/lib/mirafleet`; `EXPOSE 2222 8443`;
  `ENTRYPOINT ["/usr/bin/mirafleet"]`;
  `CMD ["central","run","-init","-data","/var/lib/mirafleet/central","-listen","0.0.0.0:2222"]`.
- **scratch, not distroless:** distroless ships Debian packages (for example `ca-certificates`,
  MPL-2.0) that the licence rule forbids bundling, and central makes no outbound TLS calls.
- Only `COPY` lines, no `RUN`: buildx builds arm64 and amd64 without QEMU.
- Labels: OCI `org.opencontainers.image.{source,version,revision,licenses=Apache-2.0,title,description}`.
  `io.modelcontextprotocol.server.name` only if Q5 puts the image in `server.json`.
- Tags: `X.Y.Z`, `X.Y`, `latest` (not for pre-releases). Signed with cosign keyless by digest;
  provenance attested by digest.
- The same image runs an actions-mode runner (`runner join` / `runner run -actions …`), which the
  compose try-it lab uses. Workspace mode is not supported in the image (needs host containerd).
- Admin in a container: `docker exec <c> mirafleet central fleet list` (same UID, so the admin
  socket check passes). GUI: on by default at `0.0.0.0:8443` inside the container with a
  self-signed certificate kept in the volume (so its fingerprint survives restarts); docs publish
  it as `-p 127.0.0.1:8443:8443`, and show mounting a real cert read-only with `-gui-cert`/`-gui-key`.
  No certificate or key is baked into the image.

### 2.6 npm wrapper `@mirastacklabs/mirafleet`
- Seven packages, all generated at release time by `relgen npm` from the release archives:
  - `@mirastacklabs/mirafleet`: `bin/mirafleet.js` (Apache-2.0, ~60 lines, no dependencies),
    `optionalDependencies` on the six platform packages at the exact same version, `mcpName`
    (Q4), `engines.node >= 18`. **No `preinstall`/`install`/`postinstall` script, no download.**
  - `@mirastacklabs/mirafleet-{linux,darwin,win32}-{x64,arm64}`: the binary, `os`/`cpu` fields,
    `LICENSE`, `NOTICE`, `THIRD_PARTY_LICENSES.txt`; `files` lists exactly these.
- Launcher: resolve `@mirastacklabs/mirafleet-${process.platform}-${process.arch}/bin/mirafleet[.exe]`
  with `require.resolve`; `child_process.spawn(bin, argv, {stdio: "inherit", windowsHide: true})`;
  forward SIGINT/SIGTERM/SIGHUP; exit with the child's code (or re-raise its signal). Clear error if
  the platform package is missing (for example `--no-optional`), naming the package to install.
  stdout untouched (it is the MCP stream).
- Use: `npx -y @mirastacklabs/mirafleet@0.6.0 mcp -project-dir .` in any harness's MCP config.
  On Windows, harnesses that spawn without a shell need `cmd /c npx …` (documented).
- **Not for the Claude Code plugin on Windows:** npm puts a `.cmd` shim on PATH, and exec-form
  hooks need a real `.exe` (integrations/claude-code/README.md). Windows plugin users install
  `mirafleet.exe` with `install.ps1` or the zip.
- Publish with provenance (`npm publish --provenance --access public`) from the release workflow,
  using npm trusted publishing (OIDC) when available for all seven packages (§9).

### 2.7 Homebrew tap `mirastacklabs-ai/homebrew-tap`
- A **formula** `Formula/mirafleet.rb` (Q3), rendered by `relgen brew` from `checksums.txt`:
  `on_macos`/`on_linux` × `on_arm`/`on_intel` blocks with the archive URL and sha256,
  `bin.install "mirafleet"`, a `test do` running `mirafleet version`. Works on macOS and Linux.
- Not goreleaser `homebrew_casks`: casks are macOS-oriented and are quarantined by Gatekeeper,
  so unsigned binaries need an `xattr` hook that bypasses Gatekeeper. A formula is not
  quarantined. Not goreleaser's formula section: deprecated.
- Pushed by the `brew` job (§7) with a token scoped to the tap repo. Skipped for pre-releases.

### 2.8 `install.sh` and `install.ps1`
- `scripts/install.sh` (POSIX sh, shellcheck clean), uploaded as a release asset:
  - Detects `uname -s`/`-m` (linux, darwin; amd64, arm64). Windows → points to `install.ps1`.
  - Version: `-v vX.Y.Z` or latest (resolved from the `releases/latest` redirect, never from a
    JSON API parse). `-b DIR` install dir (default `/usr/local/bin` if writable, else
    `~/.local/bin`; never runs `sudo` itself, says what to run).
  - Downloads the archive and `checksums.txt` over HTTPS (`curl -fsSL --proto '=https' --tlsv1.2`
    or `wget --https-only`) into a `mktemp -d` dir removed on exit.
  - **Always** verifies sha256 (`sha256sum` or `shasum -a 256`); refuses if neither exists, if the
    archive is not listed, or on mismatch. Extracts only the `mirafleet` entry.
  - If `cosign` is on PATH (or `--verify-signature` is given, then it is required), verifies
    `checksums.txt` with `checksums.txt.sigstore.json` against identity
    `https://github.com/mirastacklabs-ai/mirafleet/.github/workflows/release.yml@refs/tags/<tag>`
    and issuer `https://token.actions.githubusercontent.com`.
  - Prints the installed path and `mirafleet version`. `MIRAFLEET_INSTALL_BASE_URL` (test only,
    documented) points at a local `file://` dist for tests and the test lab.
- `scripts/install.ps1` (Windows PowerShell 5.1 and pwsh 7): same flow with
  `Invoke-WebRequest` and `Get-FileHash -Algorithm SHA256`; installs to
  `%LocalAppData%\Programs\mirafleet\mirafleet.exe`; adds that dir to the **user** PATH (not
  machine) only with `-AddToPath`; never needs admin.
- Docs show "download, read, then run" first and the one-liner second.
- **Quarantine (Q7: no notarization or Authenticode).** Binaries are unsigned by Apple or
  Microsoft; integrity comes from checksums, cosign signatures and provenance. The docs say:
  brew, npm, `install.sh` and `install.ps1` are not affected (none of them marks the file as
  downloaded from the internet). Only a zip downloaded in a browser is, with a one-line fix:
  macOS `xattr -d com.apple.quarantine mirafleet`; Windows `Unblock-File .\mirafleet.exe` (or
  Properties → Unblock), best run on the zip before extracting. Verify the checksum first.

### 2.9 `tools/relgen` (release generator, stdlib only)
A small `package main` in the main module under `tools/relgen/`, never linked into
`mirafleet` (it is a separate main package). Subcommands, each with golden-file tests:

| Subcommand | Does |
|---|---|
| `bump X.Y.Z` | rewrites the versioned files of §2.1 (JSON via encoding/json round trip, the Go const by exact-line replace) |
| `check vX.Y.Z` | all versioned files agree with the tag; `TARGETS` in dev.sh == goreleaser targets; marketplace `ref` == tag |
| `licenses DIR OUT` | assembles `THIRD_PARTY_LICENSES.txt` from `go-licenses save` output (union over the six targets) plus `licenses/extra/` |
| `npm DIST OUT VERSION` | the seven npm package dirs from the archives in `DIST` (verifies each archive against `checksums.txt` first) |
| `brew DIST OUT VERSION` | `Formula/mirafleet.rb` from `checksums.txt` |
| `serverjson VERSION` | writes / checks `server.json` |

Run through `scripts/dev.sh go run ./tools/relgen …` (container). The release workflow uses the same.

### 2.10 Third-party licences
- `scripts/dev.sh licenses-report` runs `go-licenses save ./cmd/mirafleet` per target (same pinned
  go-licenses v1.6.0 as `licenses`) and `relgen licenses` → `dist/THIRD_PARTY_LICENSES.txt`:
  for every linked module, name, version, SPDX id and the **full licence text** (Apache-2.0 §4
  requires passing on the MIT/BSD notices).
- `licenses/extra/` (checked in, reviewed by hand) covers what go-licenses cannot: the ignored
  `modernc.org/mathutil` (BSD-3-Clause) and `github.com/segmentio/asm` (MIT-0), the musl-derived MIT
  notice in `modernc.org/libc` (M2.md §6.3), and the GUI's embedded assets from M4 (htmx licence,
  Oswald and JetBrains Mono OFL-1.1 texts). A relgen test fails if an `--ignore`d module in dev.sh
  has no `licenses/extra/` entry, or if an embedded asset listed by M4 has none.
- The file ships in every archive, package (`/usr/share/doc/mirafleet/`), npm platform package
  and the image. NOTICE gains one line pointing at it.

### 2.11 Tests for distribution (all local, containers only)

| Target (`scripts/dev.sh …`) | What it proves | Runs in |

### 2.12 CI (`.github/workflows/ci.yml`, plus `orchestrator.yml`)
- Triggers: `push` to main, `pull_request` (never `pull_request_target`). Top-level
  `permissions: contents: read`; no job gets a secret. Every action pinned by full commit SHA with
  a version comment (reuse the SHAs already in `orchestrator.yml`; resolve new ones with
  `gh api repos/<owner>/<repo>/git/ref/tags/<tag>` at implementation time, peeling annotated tags).
  `persist-credentials: false` on checkout. Concurrency per ref.
- Jobs on `ubuntu-latest`, all through `scripts/dev.sh` so CI equals local:
  `gate` (fmt, build, vet, test, cross), `licenses` (+ `licenses-report`), `vuln`, `lint`
  (`lint-sh`, `lint-actions`), `integration` (privileged containerd harness; the runner VM is
  throwaway, so the dev.sh warning about bare hosts does not apply), `dist` (`release-snapshot`,
  `pkgtest`, `installtest`, `image`, `npmtest`, `relgen check` with the current versions),
  `e2e-systemd` (below).
- `e2e-systemd`: on the runner VM itself (it has systemd): `sudo dpkg -i` the snapshot `.deb`;
  enable central; create a fleet and token as `mirafleet`; join with the shipped example
  `actions.yaml`; start `mirafleet-runner`; approve; operator code; `mcp login` as the CI user;
  `mcp api action.run`; one MCP stdio `tools/call` with the built binary; the GUI answers on
  8443 under the shipped strict unit (self-signed certificate, fingerprint as logged, a session
  survives a central restart); `dpkg -r` keeps `/var/lib/mirafleet`. Ports are fixed inside the
  VM only (throwaway).
- `orchestrator.yml`: add `./integrations/...` to `PKGS` once `.gitattributes` lands (F-45); add
  an `install.ps1` test (from a `file://` snapshot built in the job) on `windows-latest`, and the
  npm launcher test via `actions/setup-node` (pinned) on `windows-latest` and `macos-latest`;
  `brew style` + `ruby -c` on the rendered formula on `macos-latest`.
- `.github/dependabot.yml`: `github-actions` and `gomod`, weekly, PRs only (dependabot keeps the
  SHA pins current; PLAN's dependency list still needs the user for any new module).

### 2.13 Release workflow (`.github/workflows/release.yml`)
Trigger: push of a tag `v*` (tag pushes are restricted by a repository ruleset, §9). Jobs:

| Job | Needs | Permissions | Environment | Does |
|---|---|---|---|---|
| `verify` | — | contents: read | — | tag is on `main`; `relgen check <tag>`; CI for that commit is green (`gh api` check-runs) |
| `build` | verify | contents: read | — | goreleaser `release --skip=publish,sign` in the tools image → `dist/` uploaded as a workflow artifact; licences report |
| `draft` | build | contents: write, id-token: write, attestations: write | `release` | cosign keyless sign `checksums.txt`; `actions/attest-build-provenance` for every archive and package; create the **draft** GitHub release with all assets, `install.sh`, `install.ps1` |
| `publish-release` | draft | contents: write | `release` | the user reviews the draft, then this job un-drafts it |
| `image` | publish-release | packages: write, id-token: write, attestations: write | `release` | buildx push to ghcr; cosign sign by digest; provenance attestation pushed to the registry |
| `npm` | publish-release | contents: read, id-token: write | `release` | `relgen npm` from the release archives; `npm publish --provenance` platform packages first, then the wrapper; dist-tag `next` for pre-releases |
| `brew` | publish-release | contents: read | `release` | `relgen brew`; commit and push to the tap with `HOMEBREW_TAP_TOKEN`; skipped for pre-releases |
| `mcp-registry` | npm (+ image if Q5) | contents: read, id-token: write | `release` | `mcp-publisher login github-oidc`; `mcp-publisher publish server.json`; skipped for pre-releases |

- The `release` environment has the user as required reviewer, so **each** outward job waits for
  an explicit approval in the GitHub UI, in order. Rejecting one stops that channel only.
- goreleaser never runs with publish credentials: `build` has none, and only the small jobs
  after it hold one credential each.
- Pre-releases (`-rc.N`) run the same path as a rehearsal (Q8): GitHub pre-release, ghcr tag
  without `latest`, npm `next`, no Homebrew, no registry.

## 3. First-run quickstart (`docs/QUICKSTART.md`, also in every archive)
Uses the guide's running example (Acme, `central.example.com:2222`, fleets `dev`/`prod`, runners
`build-1`/`db-1`, operator `alice`). Four parts, each ending with a "check it worked" line.

1. **Central (Linux).** Install: `.deb`/`.rpm`, or `install.sh` + copy the unit from
   `/usr/share/doc`, or the OCI image. Firewall first: 2222 open to runners and operators, 8443
   only to admins (or bind the GUI to `127.0.0.1` in `/etc/mirafleet/central.env`). Optionally set
   `-gui-cert`/`-gui-key` there. `systemctl enable --now mirafleet-central`, then
   `journalctl -u mirafleet-central` shows the SSH host-key fingerprint, the GUI certificate
   fingerprint and the one-time setup token (exact log lines and the token's lifetime as in
   M4.md). Admin commands as `sudo -u mirafleet mirafleet central …`.
2. **GUI bootstrap.** Open `https://central.example.com:8443` (or, when bound to localhost,
   `ssh -L 8443:127.0.0.1:8443 central.example.com` and `https://127.0.0.1:8443`). The browser
   warns about the self-signed certificate: compare the fingerprint it shows with the one from
   the journal, and continue only if they match. Enter the setup token and create the one admin
   account (steps and wording copied from M4.md at implementation time, not invented here).
   Sessions survive a restart (SQLite). Create fleet `dev` (actions) and a join token in the GUI
   or with the CLI.
3. **Runner (Linux).** Install the package; `cp /usr/share/doc/mirafleet/examples/actions.yaml
   /etc/mirafleet/` and edit; `printf '%s\n' "$TOKEN" | sudo -u mirafleet mirafleet runner join
   central.example.com:2222 -name db-1 -data /var/lib/mirafleet/runner -token -`;
   `systemctl enable --now mirafleet-runner`; approve in the GUI. Workspace variant: containerd
   installed, `workspace.yaml` from the example, join as root with `-data /var/lib/mirafleet/runner-ws`,
   `mirafleet-runner-workspace`.
4. **Operator (macOS, Linux, Windows).** Install: `brew install mirastacklabs-ai/tap/mirafleet`,
   `install.sh`, `install.ps1`, or npm (not for the Windows plugin). `mirafleet mcp login
   central.example.com:2222 -name alice -code -` with the code from the GUI. Claude Code:
   `/plugin marketplace add mirastacklabs-ai/mirafleet`, `/plugin install mirafleet@mirastacklabs`,
   then `/mirafleet list my fleets`. Other harnesses: the `npx` snippet or
   `integrations/<harness>/README.md`.

Plus two sections for testing before anything is published:
- **Test lab on a Mac:** a separate colima profile as a disposable Linux VM with systemd
  (`colima start -p mirafleet-lab`; `--runtime containerd` for a workspace runner), the snapshot
  `.deb` copied in, central + runner inside, `mirafleet mcp` on the Mac (from `dist/`) dialling the
  VM. Never the dev profile, so the dev VM is never changed.
- **One-machine try-it:** `deploy/compose/compose.yaml` (central + actions runner from the image;
  2222 and 8443 published on `127.0.0.1` only; GUI at `https://127.0.0.1:8443`, fingerprint and
  setup token from `docker compose logs central`).
- **Downloaded a zip in a browser?** The quarantine one-liners of §2.8.
- **Uninstall:** per channel; data in `/var/lib/mirafleet` is kept until deleted by hand.

## 13. Risks

| Risk | Mitigation |
|---|---|
| goreleaser OSS feature churn (deprecations before v3) | pin the version; use only builds/archives/nfpm/checksums/sboms/signs/release; brew, image and npm are ours |
| npm trusted publishing needs an existing package or changes its rules | `NPM_TOKEN` fallback for the first publish only, deleted after; checked at P1 |
| npm version burned after a bad publish | rc rehearsal to `next`; `npmtest` before any publish |
| Windows: npm `.cmd` shim cannot run exec-form hooks | `install.ps1` + zip for plugin users (Q9) |
| Browser-downloaded zips are quarantined (Gatekeeper, SmartScreen); no Apple/Microsoft signing (Q7) | docs lead with brew, npm and the install scripts, which are not affected; one-line `xattr` / `Unblock-File` fix after the checksum check |
| GUI on `0.0.0.0:8443` by default exposes a login page to the network; self-signed cert invites click-through | firewall note in `central.env`, postinstall message and quickstart; fingerprint check on first visit; `127.0.0.1` bind and `-gui-cert`/`-gui-key` documented; compose lab binds `127.0.0.1` only |
| Package scripts differ across distros | one POSIX script set; four-distro `pkgtest`; real systemd in `e2e-systemd` |
| Strict central sandbox breaks a feature (GUI cert generation and SQLite sessions, SQLite WAL, admin socket) | `e2e-systemd` exercises all of them under the shipped unit |
| Docker socket used for image builds in the colima VM | VM-confined like the integration harness; CI VMs are throwaway |
| Wrong commit tagged, or versions drift | `verify` job (tag on main, CI green, `relgen check`); tag ruleset |
| Marketplace `ref` points at a tag that does not exist yet (between bump commit and tag) | tag right after the bump commit; window of minutes; `relgen check` in CI warns until tagged |
| MCP Registry schema or publisher changes | pin `mcp-publisher`; confirm the schema URL in R3; registry step last and skippable |
| go-licenses misses assets and ignored modules | `licenses/extra/` with a test tying it to dev.sh `--ignore`s and M4's asset list |
| M4 details (GUI flag, bootstrap) not final when M6 starts | R7, R8 and R15 read M4.md and copy its names; review checks they match the code |
| Low disk on the Mac | `m6check` removes `dist/`, test images and volumes at the end |
