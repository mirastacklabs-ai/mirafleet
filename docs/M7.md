> **North star (the user's words):** "AI inference stays on the local Mac (the orchestrator); all
> tool calls run on the remote VM via central. Today the repo code, the credentials and Claude Code
> all live on the same Mac. We are simply moving the credentials to central, and the repo code and
> tool calls to the remote VM, all connected via central."

## 1. Decided (recorded, not re-asked)
1. **Host mode, one runner = one OS user on one VM:** a new workspace executor `host`. `mirafleet
   runner` runs as an ordinary unprivileged user (e.g. `dev`), enrols with its own join token, keeps
   its config and state under that user's XDG dirs, and runs every tool call as that same user. No
   root, setuid or capabilities at runtime; no containers. More runners = a new VM, or a new user on
   the same VM enrolled separately (`dev`, `qa`), isolated by normal Unix permissions (0700 homes).
   One directory per session simply persists on disk. The VM is the boundary (dedicated VM
   accepted). M3's container mode is unchanged.
2. **Dropped from M7:** Docker/Podman executor (Docker adoption comes via M6: image on
   `docker.io/mirastack/mirafleet` + Compose; the earlier Docker decisions become M6/later notes),
   new gVisor/Kata work, egress allowlisting in host mode (use the VM's firewall), volume retention.
3. **Credentials on central**, like CI/CD secrets: own GUI page and CLI, write-only and masked
   (values never shown again), encrypted at rest with a key from an environment variable at
   bootstrap. The admin assigns each credential to runners (VMs) or to a whole fleet (effective =
   union). Central delivers assigned secrets to the runner over the existing SSH connection; the
   runner keeps them out of reach of the agent user.
4. **Use without exposure:** SSH via a per-session ssh-agent socket (key never on disk for the agent
   user; host binding required by default, `off` per credential for OpenSSH < 8.9); HTTPS via a
   TLS-terminating broker in a local proxy for credential hosts only (per-session CA, combined CA
   bundle, `SSL_CERT_FILE`, `GIT_SSL_CAINFO`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`, JVM
   options); the broker does the registry token exchange, so the agent never sees a JWT. Usage
   limits come from the credential's own scope in GitLab; mirafleet adds no path/ref rules. SSH
   residual risk accepted and documented. Rotation: reload without restart, expiry warnings,
   opt-in GitLab self-rotate. Audit: runner-local JSONL + aggregated rows on central (source
   `runner`). Operators see names/kinds/hosts/status only; fingerprints and expiry are admin-only.
   Placement only on runners holding every requested credential; `workspace_open` may narrow,
   never widen. The runc setns egress listener stays as is for container mode.
5. **Features:** background jobs (start/status/tail/cancel); full output kept with paging/tail/grep
   (never a silent cut); tool parity with Claude Code (Bash foreground + background shells with
   output polling and kill, Read with line ranges and image/binary handling, Write, Edit,
   MultiEdit, Grep with ripgrep-like semantics in Go, Glob, LS, NotebookEdit) plus upload/download
   Mac ↔ VM. The plugin steers Claude to the remote tools for a remote project (skill, optional
   PreToolUse deny hooks); the MCP server works with no hooks.
6. **Handled by the coordinator in M6/PLAN:** no telemetry, DCO, version skew same + previous minor,
   automatic SQLite backup before migrate, PR + auto-merge, docs in the GitHub wiki, tested MCP
   configs for six more harnesses, M5 marked done.

## 2. Acceptance story
A private GitLab (corporate CA, HTTPS and SSH) is reachable only from the VM. The VM runs
`mirafleet runner` in host mode. The developer opens a project on the Mac whose `.mirafleet.yaml`
says `remote: true`; Claude Code clones over SSH and HTTPS, edits, runs a long build as a background
job, commits and pushes, with no repo file and no command on the Mac, and no secret in any tool
result, log, audit row or workspace-readable file.

## 3. Host mode

### 3.1 Shape (Q2)
- `workspace.yaml` `executor: host`; fleets use workspace mode with executor `host`. Sessions,
  sticky open, placement, ownership, audit, reaper and `workspace.*` methods are reused unchanged.
  Host-executor fleets cannot be guarded (Q10). Defaults follow XDG (`$XDG_CONFIG_HOME/mirafleet/`,
  `$XDG_STATE_HOME/mirafleet/`), so a runner needs nothing outside its user's home. Below,
  `<sess>` = `$XDG_STATE_HOME/mirafleet/sessions/<sid>/` (0700): job logs, outputs, sockets, CA.

```yaml
# ~dev/.config/mirafleet/workspace.yaml
executor: host
concurrent: 8
host:
  root: ~/work                  # one dir per session (or per workdir, Q4); 0700
  cleanup: {delete_after: 720h} # Q5; 0 = never
  job_max: 12h                  # background shells, <= 24h
env_allow: [LANG, LC_ALL, TERM, CI, GOFLAGS, NODE_ENV]
```

### 3.2 One OS user per runner; hiding secrets from the same uid (Q1)
- `mirafleet runner join` and `runner run` run as the user itself; tools run as that user: what
  the agent can touch is exactly what that user can touch, like Claude Code on a laptop.
- **Start-up hardening:** `prctl(PR_SET_DUMPABLE, 0)` first thing (same-uid processes then cannot
  `ptrace` the runner or open `/proc/<runner>/{mem,environ,fd,maps,root}`; core dumps off),
  `RLIMIT_CORE=0`, refuse to start as uid 0 or with any capability, refuse if `$HOME` or the state
  dir is group/world-writable. Secrets live only in runner memory: never on disk, never in env or
  argv, never in a child's environment.
- **Children:** clean environment (only `env_allow` names, the runner-set tool env of §4.4, `HOME`,
  `USER`, `PATH`, `LANG`), new session and process group (`Setsid`), only fds 0–2 inherited; children
  are normal dumpable processes of the same user.
- **Exposed to the agent:** the per-session ssh-agent socket (0600, in a 0700 dir) and the local
  HTTPS broker; nothing else from the runner.
- **Honest limits:** root on the VM can read anything (runner memory included). Yama `ptrace_scope`
  is not relied on (non-dumpable already blocks same-uid ptrace; scope ≥ 1 is extra). The same uid
  can kill the runner (availability, not secrecy) and edit the runner's config (only its own runner).
- **The gap (Q1): the runner's own enrolment key.** It must persist on disk to reconnect, so the
  same uid can read it, connect to central as this runner and receive `creds_sync`, i.e. the
  secrets. Same-uid tricks (keyring, systemd credentials, private mount namespaces) do not close it:
  the user's systemd/cron/ssh can start a process outside any namespace. Options in Q1; the clean
  fix is a **runner/tools user pair** (`dev-mf` holds the key and secrets, `dev` runs tools through a
  small `mirafleet runner tools` daemon that the runner talks to over a peer-checked socket; still
  no root, setuid or capabilities at runtime). With the decided single-user shape central at least
  detects key reuse: a second connection while one is live is refused and audited
  (`runner.duplicate_login`), and the GUI flags it.

### 3.3 Install options and a second runner on the same VM
- **systemd user unit** (`~/.config/systemd/user/mirafleet-runner.service`, `ExecStart=mirafleet
  runner run -workspace %h/.config/mirafleet/workspace.yaml`, `KillMode=process` so background shells
  survive restarts, `Restart=on-failure`), enabled with `systemctl --user enable --now` and
  `loginctl enable-linger dev` (an admin step, once).
- **System unit with `User=`** (`/etc/systemd/system/mirafleet-runner@.service`, `User=%i`,
  `ExecStart=… -workspace /home/%i/.config/mirafleet/workspace.yaml`, `KillMode=process`): one
  instance per user, `systemctl enable --now mirafleet-runner@dev`.
- **Second runner:** `useradd -m qa` (home 0700), as `qa`: `mirafleet runner join central:2222 -name
  vm1-qa -token -`, copy `workspace.yaml`, start its unit (`mirafleet-runner@qa` or its user unit).
  Central sees two runners; credentials are assigned to each separately.

### 3.4 Sessions and directories (Q3, Q4, Q5)
- All sessions of one runner share its user: one developer or one team that trusts each other (Q3);
  separate trust = separate runner user or VM.
- Directory = `<root>/<slug>` from the session id (or `workdir:` in `.mirafleet.yaml`, Q4), 0700.
  `HOME` is the user's real home (shared caches such as `~/.m2`, `~/.cache/go-build`, as on a laptop).
- `workspace_close` (and the idle reaper) kills the session's process groups and closes its agent
  socket and broker session; **the directory stays**. Reopening the session (or `workdir`)
  reattaches it. `workspace_list` shows dirs with size and last use.
- **Cleanup policy (explicit):** close never deletes. A daily runner sweep deletes directories not
  used for `cleanup.delete_after` (default 30 d, Q5); tool results warn 3 days before. Explicit
  delete: `workspace_close {delete: true}` (owner), `mirafleet runner host prune [-older-than D]
  [-yes]` (dry run without `-yes`), admin `workspace.kill -delete` on central.

### 3.5 Bash, background shells and jobs (Q6, Q11)
- `bash{command, timeout_s (default 120, ≤ 10 min like Claude Code), description,
  run_in_background}` runs `bash -lc` (fallback `sh -c`) in the session's current directory. The
  runner persists the cwd per session (a wrapper reports the final `pwd` on fd 3), like Claude
  Code's Bash; env does not persist (Q11).
- `run_in_background: true` starts a **background shell**: `mirafleet host-shim job` supervises it
  (own process group), writing `stdout`/`stderr` and `status.json` to `<sess>/jobs/<id>/`. `bash_output{shell_id, filter?}` returns new
  output since the last call (like BashOutput); `kill_shell{shell_id}` kills the group; `job_list`.
- Jobs survive a runner restart (`KillMode=process`; the runner re-adopts them from `status.json`,
  pid and start time, Q6). Status files belong to the agent's own user: informational only.
- Limits: 8 background shells per session, max duration per fleet (default 12 h, ≤ 24 h), log cap
  256 MiB per stream (head 1 MiB + rotating tail). A running job keeps the workspace in use
  (heartbeat `busy`, central touches the row at most every 5 min).

### 3.6 Output: never a silent cut
- Every foreground `bash` tees full output to `<sess>/out/<request_id>` (last 32 kept, ≤ 64 MiB
  each). Results carry `stdout_bytes`, `stderr_bytes`, `truncated{head, tail, omitted}` and `ref`;
  the text says how to page. `read_output{ref|shell_id, offset, limit, tail_lines, grep}` pages it.

### 3.7 File tools (Q12)
- One pure package `internal/workspace/fsops` implements the operations, run in the runner process
  (it is the same user), so OS permissions are the boundary and everything the user can see is
  reachable (parity with local Claude Code). Relative paths resolve from the session dir. FIFOs and
  devices are refused (`O_NONBLOCK` + regular-file check), so a planted FIFO cannot hang the runner.

| MCP tool | Claude Code tool | Semantics |
|---|---|---|
| `bash`, `bash_output`, `kill_shell` | Bash, BashOutput, KillShell | §3.5 |
| `read` | Read | `offset`/`limit` in lines, numbered output, 2000-line default, long lines clipped; images (png, jpg, gif, webp ≤ 5 MiB) returned as MCP image content; other binary: size, type, sha256; `.ipynb` rendered as cells with outputs |
| `write` | Write | create/replace, atomic, mode kept |
| `edit`, `multi_edit` | Edit, MultiEdit | exact `old_string` (unique unless `replace_all`); MultiEdit applies in order, all-or-nothing |
| `grep` | Grep | Go RE2, ripgrep-like: `path`, `glob`, `type` (rg's type table), `output_mode` content/files_with_matches/count, `-i`, `-n`, `-A/-B/-C`, `multiline`, `head_limit`; honours `.gitignore`, `.ignore`, hidden files skipped; bounded (100k files, 256 MiB, 30 s) |
| `glob` | Glob | `**` patterns, results sorted by mtime, gitignore honoured |
| `ls` | LS | absolute or relative path, `ignore` globs |
| `notebook_edit` | NotebookEdit | `cell_id`, `new_source`, `cell_type`, `edit_mode` replace/insert/delete; JSON preserved |
| `upload`, `download` | — | Mac ↔ VM, §3.9 |

- Container mode is not extended in M7 (north star). `fsops` is a pure package, so wiring it into
  `ctrd` later is a small follow-up (~½ day); the new tools return `unsupported` on container fleets.
- Protocol: one operator method `workspace.fs{op}` (fixed op enum) and `workspace.job_*`,
  `workspace.output_read`; transport ops to match; `confirm` rules unchanged (host fleets are never
  guarded). Audit records op, paths, sizes, SHA-256 of written data, never content.

### 3.8 Plugin steering for a remote project (Q9)
- `.mirafleet.yaml` gains `remote: true` and optional `workdir: NAME` (strict, still no addresses).
- Skill and shared command body: for a remote project use only the mirafleet tools; open the
  workspace first; read the remote repo's `CLAUDE.md`/`AGENTS.md` with `read` (Claude Code only
  loads local ones); prefer `edit`/`multi_edit`; builds over 2 min as background shells; never put
  tokens in URLs; clone with plain `git@…`/`https://…` URLs (credentials are injected).
- Optional `PreToolUse` hook (Claude Code plugin): when the project file says `remote: true`, it
  **denies** local `Bash`, `Read`, `Write`, `Edit`, `MultiEdit`, `Grep`, `Glob`, `LS`,
  `NotebookEdit` with a reason naming the remote tool. Without hooks the skill and the MCP server
  instructions carry the same rule.

### 3.9 Upload/download (Mac side, Q13)
- Confined to the local project dir through `os.OpenRoot` (symlinks out refused); refuses `.git/`,
  `.claude/`, `.mirafleet.yaml`, `.env*`, `*.pem`, `*.key`, `id_*`, `.npmrc`, `.netrc`
  (case-insensitive on darwin/windows; Windows reserved names refused); ≤ 64 MiB; downloads 0644,
  atomic, no overwrite unless asked. Results show relative paths only.

## 4. Credentials

### 4.1 Store on central
- Kinds: `ssh-key` (OpenSSH private key + `known_hosts` lines + SSH user, default `git`),
  `https-token` (`basic` user+token, `bearer`, or `header: NAME`), `registry` (user + password/token;
  the broker does the token exchange). Each has `hosts` (`host[:port]`), optional `expires`,
  optional `rotate: gitlab_self`.
- Encrypted at rest: AES-256-GCM (stdlib), random nonce per value, AAD = credential id + version.
  Key: 32 bytes, base64 in `MIRAFLEET_SECRETS_KEY` at `central run` (Q8); only a key-check value
  (HMAC of a constant) is stored. Secrets present but key missing or wrong → central refuses to
  start. `central secrets rekey` takes the new key on stdin and re-encrypts in one transaction.
- Migration 0004: `credentials(id, name UNIQUE, kind, hosts, meta JSON, nonce, ciphertext, version,
  created_at, updated_at)`, `credential_assignments(credential_id, runner_id NULL, fleet_id NULL,
  CHECK exactly one)`, `secrets_meta(key_check)`; `fleet_workspace` rebuilt to allow executor
  `host`; audit source `runner`.
- Admin only (local admin socket, GUI); never on `api@` or MCP. Methods: `credential.set` (value
  as a body frame, never echoed), `credential.list` (masked: name, kind, hosts, assignments,
  fingerprint and expiry for admins, status per runner), `credential.delete`, `credential.assign`,
  `credential.unassign`. CLI: `central credential set NAME -kind … -hosts … < secretfile`,
  `list`, `delete`, `assign NAME -runner fleet/runner | -fleet F`, `unassign`. Audited without values.
- GUI (M4 screens): **Credentials** page (create/replace via a write-only form or file upload,
  masked list, assign to runners or fleets, per-runner delivery status); Runners detail shows
  which credentials each runner holds and their status.

### 4.2 Delivery and holding (Q8)
- Central pushes the effective set (runner assignments ∪ fleet assignments) to each active
  host-mode runner on connect and on every change, over a new `workspace@mirafleet` op `creds_sync`
  inside the authenticated SSH connection. The runner keeps values **in memory only** and replaces
  the set atomically (removed credentials stop working at once). Runner revoke: nothing is sent
  again; the connection is gone.
- Heartbeat reports names, kinds, hosts, `status` (`ok|expiring|expired|invalid`); operators see
  these in `runners.list`; fingerprints and expiry dates are admin-only.
- `workspace_open{credentials?}` may narrow to a subset; default = all held. Placement requires
  every requested credential. (A runner's sessions share its uid, Q3, so narrowing is hygiene, not
  a boundary; the boundary between trust domains is a separate runner user or VM.)

### 4.3 SSH: per-session restricted agent
- `internal/workspace/sshagent` on `x/crypto/ssh/agent`: `List` and `Sign` only; signs only SSH
  user-auth requests for the credential's user; with host binding (`session-bind@openssh.com`,
  OpenSSH ≥ 8.9) the server host key must be in the credential's `known_hosts`; `off` per
  credential. No add/remove/lock/export.
- Socket `<sess>/agent.sock` (0600, dir 0700; other users on the VM cannot reach it); the runner
  sets `SSH_AUTH_SOCK` and `GIT_SSH_COMMAND=ssh -F <sess>/ssh_config` (pinned `known_hosts`,
  `IdentitiesOnly`, `IdentityAgent`). The key never touches disk.
- **Residual (accepted, documented):** while a session is open the agent can use the key against the
  pinned hosts with the key's GitLab permissions; and the dev user can SSH anywhere the VM's
  firewall allows with keys it brings itself.

### 4.4 HTTPS and registries: broker in a local proxy
- A runner-local proxy on `127.0.0.1:<port>`; each session gets `HTTPS_PROXY`/`HTTP_PROXY` with a
  per-session proxy password (identifies the session and keeps other users on the VM, e.g. `qa`,
  off this runner's broker, since loopback ports are shared). Hosts without
  a credential are raw CONNECT tunnels (no allowlist: the VM's firewall decides). Credential hosts
  are terminated with a per-session CA (ECDSA P-256, NameConstraints = that session's credential
  hosts, key in runner memory only), upstream TLS verified against the system pool + corporate CA,
  the header injected, client auth headers replaced, redirects never followed. HTTP/1.1 only.
- Registry token exchange: on a `401 Bearer` challenge from a registry credential host, the broker
  fetches the token from the realm with the stored credential, caches it per scope and injects
  `Authorization: Bearer`; the client never sees a 401 or a JWT.
- Env set by the runner (agent-set env cannot override these names): `SSL_CERT_FILE`,
  `GIT_SSL_CAINFO`, `CURL_CA_BUNDLE`, `REQUESTS_CA_BUNDLE`, `PIP_CERT`, `NODE_EXTRA_CA_CERTS`,
  `JAVA_TOOL_OPTIONS` (proxy properties); bundle = VM system bundle + session CA at
  `<sess>/ca.pem`. JVM truststore: keytool recipe in the skill.

### 4.5 Rotation and audit (Q7)
- A replaced value is pushed by `creds_sync` and used at once. Expiry warnings 14 d ahead (GUI,
  heartbeat status, tool results naming the credential).
- Opt-in `rotate: gitlab_self`: one designated runner calls `POST /projects/:id/access_tokens/self/rotate`
  (token needs `self_rotate`) when < 7 d remain and sends the new value to central in an
  `events@mirafleet` `credential.rotated` event; central re-encrypts and re-syncs. Only for that
  credential on that runner.
- Every use is logged runner-local (JSONL) and sent as aggregated events (per session, credential,
  host, status, 60 s window; ≤ 128 events/64 KiB per batch; per-runner caps; `events.dropped`).

### 4.6 Threat model (prompt-injected agent on the VM)

| Attack | Defence | Residual |
|---|---|---|
| Read the secret (files, env, `/proc`, runner memory, `git credential fill`, `GIT_TRACE_CURL`) | memory only; runner non-dumpable (`PR_SET_DUMPABLE 0`), no core dumps; clean child env | none at the process level |
| Read the runner's enrolment key (same uid) and log in to central as the runner to get `creds_sync` | **open gap, Q1**: duplicate-login refusal + audit + GUI flag (decided shape); the runner/tools user pair closes it | with the decided shape: a determined agent can obtain the runner's assigned secrets |
| Kill or reconfigure the runner (same uid) | none needed for secrecy | availability of its own runner |
| Export the key from the agent socket; use it as a signing oracle | no export; user-auth only; host binding | public key visible |
| Use the credential beyond its purpose | GitLab scope of the token/deploy key (admin's choice; docs: `write_repository` only, project-scoped deploy keys) | whatever that scope allows, while a session is open |
| See a registry JWT | broker does the exchange | none |
| Mint certs for other hosts | per-session CA key in runner memory, NameConstraints | none |
| Exfiltrate code | VM firewall; model provider seeing code accepted | anything the firewall allows |
| Read another session's files | same runner = same uid (Q3) | same trust domain by design |
| Reach another runner user's (`qa`) files, agent socket or broker | 0700 homes and session dirs, 0600 sockets, per-session proxy password | root on the VM |
| Central DB copied | AES-GCM, key only in central's env | key theft = secrets |
| Central compromised | holds all secrets | single trust point (documented) |
| Root on the VM | holds the session's secrets in memory | dedicated VM accepted |
